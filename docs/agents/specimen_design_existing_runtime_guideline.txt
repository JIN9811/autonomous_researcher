============================================================
0. Current Runtime Snapshot (Phase 1)
============================================================

This repository already has the target Topology implemented for Phase 1:
- Stage routing is defined by the active LangGraph config in `graphs/configs/*.yaml`; the default closed-loop route is design -> specimen -> vision -> manipulation -> equipment -> analysis -> knowledge -> bo -> guardian.
- BO Agent is a real configured LangGraph stage after KnowledgeAgent and before GuardianAgent.
- MainLoop keeps full-cycle execution through `LangGraphRunLoop`, and Guardian continue/stop/error transitions are graph-configured.
- `orchestrator_plan` LLM calls are only for discussion-level orchestration in Live GUI, not stage execution logic.
- No new top-level stage nodes are required for the downloaded algorithm.

Design/Specimen contract currently used:
- `DesignAgent` emits `experiment_spec` and `rationale`.
- `SpecimenMakingAgent` validates/creates geometry and returns `specimen_result` and `protocol_note`.
- `guardian` still owns stop/recover decisions and returns `guardian`.

Phase 1 execution contract:
- Live GUI planning route follows the active graph transition order after the operator trigger.
- Test-mode planning handoff runs 5 cycles. In the default graph each cycle executes Design -> Specimen -> Vision -> Manipulation -> Equipment -> Analysis -> Knowledge -> BO -> Guardian. If the active graph changes, the Live GUI route text and post-Specimen tail must change with it.
- For every test-mode design cycle, the Design Agent message must show two visual artifacts: the previous shape and the next shape. Cycle 1 uses a baseline reference when no previous physical/specimen result exists.
- From cycle 2 onward in test-mode closed-loop runs, generated STL models must not include physical top/bottom cap skins. CAE still applies top/bottom platens internally for boundary conditions; those platens are analysis-only and must not be added to the printed/generated specimen.
- Trigger `실험 수행` for operator-confirmed execution and trigger `테스트 모드` / `테스트모드` for LLM-assisted test-value generation.
- After trigger, emit the planning conversation in active graph order. Default graph order is:
  1) DesignAgent (produces `experiment_spec`)
  2) SpecimenMakingAgent (builds STL + mesh/manufacturability + `specimen_result`)
  3) VisionAgent (observes the 3DP output pickup area)
  4) ManipulationAgent (runs the transfer bridge/rollout)
  5) LabEquipmentAgent (runs the UTM/equipment bridge)
  6) AnalysisAgent (computes UTM/CAE closed-loop metrics)
  7) KnowledgeAgent (writes memory/RAG summary)
  8) BOAgent (uses KnowledgeAgent memory/RAG context and experiment evaluations to recommend next-cycle design constraints)
  9) GuardianAgent (validates and decides continue/stop/error)
- In the default graph, the planning transcript should emit `design_ai`, `printer_ai`, `vision_ai`, `manipulation_ai`, `equipment_ai`, `analysis_ai`, `knowledge_ai`, `bo_ai`, and `guardian` messages in that order; if the active graph changes, transcript order follows the graph.
- Keep test/hardstop safety behavior unchanged: if any agent fails, stop chain and expose failure reason.

Live GUI (planning route) behavior currently expected:
- Message `"실험 수행"` triggers Design handoff. In normal Live GUI mode this also means the generated `experiment_spec.print` requests actual upload/start on the active printer profile after SpecimenMakingAgent completes slicing/preparation. The default physical profile is Bambu Lab X2D; Prusa MK4S is used only when explicitly selected.
- Message `"테스트 모드"` or `"테스트모드"` triggers LLM-assisted value generation, then handoff.
- Message `"테스트 모드, 가상 브릿지"`, `"테스트 모드, 설치 프린터"`, or `"테스트 모드, 실제 출력"` triggers the same test-value generation and injects the matching `printer_test_path`, so SpecimenMakingAgent continues without asking the path question again.
- For `"테스트 모드, 실제 출력"`, the controller should return the Live GUI request immediately and continue the long physical-print handoff in a background task. The GUI must refresh through planning events/session state instead of waiting for selected-printer upload/start in the original fetch.
- For physical TPMS gyroid output, use the operator/profile-controlled cap setting. The default profile enables bottom-only cap skin: `bottom_cap_enabled=true`, `top_cap_enabled=false`, `top_bottom_cap=true`, `require_flat_compression_faces=false`, and `skin_thickness_mm=0.8`. Enable `top_cap_enabled` only when a flat upper compression face is explicitly required and the unsupported top skin is acceptable.
- Bare TPMS first-layer adhesion should use operator/profile-controlled first-layer and bed-temperature options by default: `first_layer_height_mm=0.2`, `slow_first_layer_enabled=true`, `first_layer_speed_mm_s=10.0`, `bed_temperature_c=60.0`, `first_layer_bed_temperature_c=60.0`. Always pass equivalent layer-height, first-layer-height, bed-temperature, and first-layer-bed-temperature settings to the active slicer; pass first-layer speed only when slow-first-layer is enabled.
- 3DP GUI saved `Test Options` values, especially `Test Specimen Size mm` stored as `test_specimen_size_mm` and `Test Unit Cell Size mm` stored as `test_unit_cell_size_mm`, are authoritative constraints for test-mode handoffs and should be preserved through DesignAgent -> Specimen Making Agent. The current compatibility storage file is `memory/prusa_print_profile.json`, but this is not a forced Prusa runtime selection.
- BOAgent must not change `cell_size_mm` during the 5-cycle test-mode planning loop. The active 3DP GUI/operator value is the loop-stable unit-cell size; BO recommendations can adjust `relative_density`, `wall_thickness_mm`, `orientation_deg`, `anisotropy_ratio`, `tpms_thickness`, and cap/skirt-related parameters, but `cell_size_mm` is filtered before the next DesignAgent cycle.
- The controller must not pass the full previous specimen as the next-cycle constraint set. Carry forward static/operator constraints only; free shape variables must be regenerated by DesignAgent or explicitly supplied by BO. This prevents the previous STL shape from being repeated for all 5 cycles.
- BOAgent must attach current/prior evaluation points to `experiment.benchmark` and treat them as already-seen candidates so the next recommended TPMS shape signature is not identical to the current one.
- BOAgent and DesignAgent must keep gyroid `relative_density >= 0.20`; values below this violate the FDM continuous-shell rule and must be clamped before SpecimenMakingAgent manufacturability checks.
- In test-mode loop cycle 2 and later, set `top_cap_enabled=false`, `bottom_cap_enabled=false`, `top_bottom_cap=false`, `skin_thickness_mm=0.0`, and `test_loop_surface_caps_disabled=true` before STL generation. This prevents unintended plates from being carried into subsequent generated specimens.
- In Live GUI `테스트 모드`, the generated print block starts with `start_immediately=false` unless `printer_test_path=installed_printer` or `printer_test_path=physical_print` is already explicitly selected, and asks SpecimenMakingAgent for one of three printer paths when no inline path is provided:
  - `virtual_bridge`: real active-slicer preparation, then virtual selected-printer upload/start-boundary validation.
  - `installed_printer`: real active-slicer preparation, actual sliced project-file upload/start, fresh printer progress observation, immediate stop, then source-bounds-derived standalone Bambu autoejection before the downstream active-cam/manipulation/vision-verification tail.
  - `physical_print`: real active-slicer preparation, `.autoeject.gcode.3mf` print-tail patching, then selected-printer upload/start for the test-generated specimen.
- Design handoff should move to Specimen stage in the planning transcript before Guardian validation.
- DesignAgent is the only Live GUI role that should render STL preview/viewer artifacts. In test-mode cycles it renders a two-card pair: previous shape and next shape.
- SpecimenMakingAgent should render manufacturing runtime state:
  - active slicer settings
  - output G-code/3MF path
  - selected-printer storage/readiness
  - selected-printer endpoint shape
  - upload/start result
  - upload/start/ejection gate result
  - `printer.prepare` step trace

Artifact handling:
- Primary planning artifacts are exposed at `/api/planning/artifacts/{run_id}/{specimen_id}/{filename}`.
- If planning-generated STL is missing, resolve and serve files from `runs/<run_id>/specimens/<specimen_id>/`.
- Use `specimen.stl`, `specimen_preview.svg`, and `experiment_spec.json` for design artifacts.
- Use `fem_contour.svg` and `cae_report.json` for AnalysisAgent CAE contour artifacts.

Test mode expectations:
- `test` run mode must be end-to-end executable without real hardware (mock tools + simulator-friendly defaults).
- `test` run mode executes 5 complete cycles by default. Guardian stops at the planned 5-cycle cap.
- Deterministic Design fallback is required in TEST mode for schema compliance.
- KnowledgeAgent output must be stored in `run_metadata["knowledge"]`; BOAgent must read that context, store `run_metadata["bo_agent"]`, and store next-cycle candidate parameters in `run_metadata["bo_recommended_constraints"]` for DesignAgent.
- `run_metadata["bo_recommended_constraints"]` must exclude `cell_size_mm` at runtime merge time. This prevents a valid first-cycle test specimen from switching unit-cell size after BO evaluation.

1. Correct Mapping into Existing Agents
============================================================

The downloaded specimen design algorithm must be decomposed into the current agents as follows.

DesignAgent:
- Owns candidate parameter generation.
- Produces state.current_experiment_spec via AgentResult.data["experiment_spec"].
- May use LLM reasoning, prior experiment memory, and deterministic fallback.
- Must remain deterministic in test mode when real LLM is disabled or unavailable.

GuardianAgent:
- Owns safety and feasibility judgment.
- Must validate design candidate fields before hardware-facing execution.
- Should read state.current_experiment_spec and latest SARM/anomaly signals.
- Must return AgentResult.data["guardian"].

SpecimenMakingAgent:
- Owns specimen artifact handoff and print-preparation delegation.
- Calls geometry/handoff tools only through ctx.tools.call(...).
- Calls printer.prepare only after a valid handoff package exists.
- Must still return AgentResult.data["specimen_result"] and "protocol_note".
- Must forward `printer.prepare` runtime details into `specimen_result`:
  - `sliced_path`
  - `slicer_settings`
  - `slicer_result`
  - `gcode_validation`
  - `printer`
  - `prusalink`
  - `print_result`
  - `ejection_result`
  - `step_trace`
- May stream `printer.prepare` step events to Live GUI through AgentContext's tool-event callback.

MCP Tools:
- Own deterministic geometry generation and validation.
- Must be registered in ToolRegistry.
- Must return dict payloads with ok/status and stable keys.

KnowledgeAgent:
- Owns memory update after analysis.
- May later store design artifact metadata, STL hash, validation reports, and handoff paths.
- Do not move design generation into KnowledgeAgent.

AnalysisAgent:
- Owns post-UTM objective computation.
- The proxy score produced by DesignAgent is not the final objective.
- Final objective is computed after equipment result exists.

Current default geometry policy:
- Default Live GUI, main GUI test mode, and underspecified orchestrator proposals should use TPMS gyroid.
- Keep explicit legacy labels such as lattice_bcc, lattice_fcc, and lattice_octet valid for compatibility.
- Map generic labels such as lattice, bending-dominated lattice, TPMS, metamaterial, compression cube, and cube to gyroid unless the operator explicitly asks for BCC/FCC/octet.
- If `preferred_geometry_type` is gyroid/TPMS and generated candidates are rejected by FDM rules, DesignAgent must produce a conservative gyroid fallback instead of falling back to honeycomb or another supported geometry. Specimen IDs and artifact paths must match the final `geometry_type`.
- TPMS gyroid uses the existing payload variables:
  - specimen_size_mm controls the bounding box.
  - cell_size_mm controls the physical gyroid unit-cell size; repeat count is derived as round(specimen dimension / cell_size_mm).
  - wall_thickness_mm and relative_density control shell threshold/thickness.
  - anisotropy_ratio changes cell count along z.
  - orientation_deg rotates the centered x/y gyroid coordinates.
  - defect_seed and defect_ratio create deterministic void defects.
  - skin_thickness_mm plus top_cap_enabled/bottom_cap_enabled create optional cap skins.
  - Default operator profile enables bottom cap only: bottom_cap_enabled=true, top_cap_enabled=false, top_bottom_cap=true, and skin_thickness_mm=0.8.
  - Disable both cap flags only when bare TPMS output is explicitly requested for the current fixture.
  - Optional tpms_surface, tpms_thickness, and tpms_resolution may be passed, but the MCP tool contract must remain geometry.generate_metamaterial_stl with the existing required keys.
- Runtime generation must emit an actual gyroid TPMS surface, not a cubical voxel hull:
  - Use the centered canonical gyroid equation `sin(xr)cos(yr)+sin(yr)cos(zc)+sin(zc)cos(xr)=0`.
  - `orientation_deg` rotates centered x/y coordinates before evaluating the canonical equation; do not fake orientation by adding unrelated phase offsets to each term.
  - Preferred backend: numpy + scikit-image marching_cubes + trimesh, when available.
  - Dependency-free backend: marching tetrahedra over `abs(gyroid_field)-tpms_thickness=0`.
  - Axis-aligned faces should be limited to optional top/bottom compression caps; the gyroid body should be dominated by curved/non-axis STL facets.
  - After mesh generation, disconnected islands must be removed by keeping the largest connected component and recording cleanup metadata.
- FDM printability is a hard precondition for generated gyroid specimens:
  - Assume the active printer profile, defaulting to Bambu Lab X2D FDM/FFF with 0.4 mm nozzle and 0.2 mm layer height unless overridden.
  - wall_thickness_mm must be at least 1.2 mm for gyroid TPMS compression specimens.
  - cell_size_mm should stay at or below 10 mm to avoid excessive unsupported span/bridging risk.
  - Default test-mode cell_size_mm comes from the 3DP GUI saved `test_unit_cell_size_mm`, defaulting to 10.0 mm unless the operator explicitly overrides it with another valid value.
  - For FDM gyroid cells, keep wall_thickness_mm / cell_size_mm at or below 0.28.
  - bottom_cap_enabled defaults to true for bed adhesion; top_cap_enabled defaults to false because unsupported top TPMS skins can sag during FDM printing.
  - top_bottom_cap is a compatibility field equal to top_cap_enabled OR bottom_cap_enabled.
  - If both cap flags are false, require_flat_compression_faces must also be false and skin_thickness_mm must be 0.0.
  - require_flat_compression_faces may be true only when both top_cap_enabled and bottom_cap_enabled are true.
  - relative_density should be at least 0.20 so the shell remains continuous enough for FDM.
  - tpms_thickness must be clamped to the physical wall/nozzle rule even if the LLM proposes a thinner value.
  - Overhang risk should assume a 45 degree FDM support threshold; if the final slicer detects worse regions, Guardian/Specimen Making should block or require support strategy.

4. Candidate Generation Policy
============================================================

DesignAgent should choose a strategy based on available memory.

Strategy selection:
- If no prior valid records exist: use deterministic DOE or seeded constrained random.
- If few prior records exist: use simple acquisition from expected proxy score and uncertainty.
- If enough prior records exist: use learning.bo_engine / learning.active_learning when available.
- If LLM or learning model fails in test mode: use deterministic fallback.

Candidate generation process:
1. Build candidate pool of 5 to 20 candidates internally.
2. Apply hard constraints.
3. Apply known failure-memory filters.
4. Estimate expected mass, print time, manufacturability, and objective proxy.
5. Rank candidates.
6. Return one selected candidate in experiment_spec.

The selected candidate must be valid enough for downstream tools, not merely descriptive text.

Proxy score guidance:
- expected_objective_proxy_score is a design-time estimate only.
- Real objective must be computed by AnalysisAgent after equipment testing.

5. Pre-Geometry Guardian Validation
============================================================

GuardianAgent should validate state.current_experiment_spec before allowing risky continuation.

Hard reject conditions:
- Missing candidate_id or specimen_id.
- geometry_type unsupported by configured geometry tool.
- specimen_size_mm exceeds printer or UTM fixture limits.
- wall_thickness_mm < max(2.0 * nozzle_diameter_mm, minimum_feature_size_mm).
- cell_size_mm < 3.0 * wall_thickness_mm.
- expected_mass_g > max_mass_g.
- expected_print_time_min > max_print_time_min, unless policy explicitly allows it.
- top_bottom_cap is false when flat compression faces are required.
- candidate matches a known failure pattern in FailureMemory.

Guardian output must keep this shape:

AgentResult.data = {
  "guardian": {
    "decision": "continue" | "stop" | "error",
    "reason": "...",
    "precursor": float,
    "policy_note": "...",
    "design_validation": {
      "status": "pass" | "fail" | "warning",
      "reject_reasons": [...],
      "warnings": [...]
    }
  }
}

Important:
- The current RunLoop routes guardian after knowledge.
- Do not add a new stage before specimen just to validate design.
- If early design validation is needed before specimen, implement it inside SpecimenMakingAgent or as a policy helper used by SpecimenMakingAgent, while preserving the existing stage flow.

============================================================
7. SpecimenMakingAgent Internal Flow
============================================================

SpecimenMakingAgent must keep:

AgentResult.data = {
  "specimen_result": response,
  "protocol_note": protocol_note
}

Recommended internal flow:

1. Read candidate from state.current_experiment_spec.
2. Validate that required candidate fields exist.
3. Derive output_dir under existing run directory conventions:
   - runs/{run_id}/specimens/{specimen_id}/
4. Call geometry.generate_metamaterial_stl through ctx.tools.call.
5. If generation fails:
   - raise a structured exception or otherwise enter the existing RunLoop retry/fatal-error path.
   - include failure context in the exception message or logged payload.
   - do not call printer.prepare.
6. Call geometry.check_mesh_quality.
7. If mesh fails:
   - raise a structured exception or otherwise enter the existing RunLoop retry/fatal-error path.
   - include reject reasons in the exception message or logged payload.
   - do not call printer.prepare.
8. Call geometry.check_manufacturability.
9. If manufacturability fails:
   - raise a structured exception or otherwise enter the existing RunLoop retry/fatal-error path.
   - include reject reasons in the exception message or logged payload.
   - do not call printer.prepare.
10. Call artifact.create_specimen_handoff.
11. If handoff fails:
   - raise a structured exception or otherwise enter the existing RunLoop retry/fatal-error path.
   - do not call printer.prepare.
12. Call printer.prepare with at least:
   - specimen_id
   - stl_path
   - handoff_package_path
   - printer_profile
   - material
   - slicer_profile_hint
13. Return specimen_result containing:
   - ok
   - tool result from printer.prepare
   - specimen_id
   - stl_path
   - handoff_package_path
   - mesh_status
   - manufacturability_status
   - expected_mass_g
   - expected_print_time_min
   - geometry_hash

The existing validation policy does not require specimen_result, but downstream UI/logging expects the key to remain stable.

Important failure-handling rule:
- The current RunLoop validates required payload keys, merges data, logs agent_result, and advances to the next stage.
- It does not stop only because AgentResult.success is false.
- Therefore hard specimen failures must not be represented only as AgentResult(success=False).
- Hard failures must raise an exception or use an equivalent mechanism that triggers the existing retry/fatal_error path.
- Recoverable warnings may be returned inside specimen_result with ok=true and warning fields.

In test mode:
- Use deterministic candidate generation.

Required test scenarios:

2. Too-small wall thickness fails before printer.prepare.

5. Mesh validation failure returns success=False and reject reasons.
6. Manufacturability failure returns success=False and reject reasons.
7. Missing required candidate field returns success=False without hardware call.
8. Cache hit reuses STL and still creates handoff.

============================================================
12. Error Handling Policy
============================================================

Errors must be structured and visible in logs.

Recoverable errors:
- Candidate missing optional field.
- Geometry tool transient failure.
- Cache miss.
- Mesh/manufacturability warning.

Hard failure for specimen stage:
- Missing required candidate fields.
- Invalid handoff package.
- Mesh validation fail.
- Manufacturability validation fail.
- printer.prepare failure in live mode.

SpecimenMakingAgent should not silently convert invalid geometry into ok=True.
SpecimenMakingAgent should not rely on AgentResult(success=False) alone for hard failures.
Hard failures should raise so the existing RunLoop can log the exception, retry within budget, and emit fatal_error if retries are exhausted.

Recommended failure payload:

specimen_result = {
  "ok": false,
  "stage": "specimen",
  "failure_type": "mesh_validation_failed",
  "reject_reasons": [...],
  "warnings": [...],
  "candidate_id": "...",
  "specimen_id": "...",
  "stl_path": null,
  "handoff_package_path": null
}

This payload is useful for logs or exception context. It is not sufficient by itself if the stage must stop.

2026-05-29 Update: Design Agent Agentic Loop Contract
============================================================

DesignAgent is now the first decision node of the experiment design loop, not only a single printable-spec generator.
The existing `experiment_spec` remains the authoritative downstream handoff. The new structured fields are explanatory and auditable evidence around that handoff.

DesignAgent AgentResult.data now includes:
- `experiment_spec`: authoritative selected candidate consumed by SpecimenMakingAgent.
- `rationale`: short execution rationale and LLM review/degraded note.
- `design_report`: `design_report.v1` structured report.
- `design_candidate`: `design_candidate.v1` handoff packet to SpecimenMakingAgent.
- `handoff_packet`: same design handoff packet, retained for generic runtime consumers.
- `candidate_ledger`: candidate pool ledger copied from `design_report.candidate_generation.candidate_ledger`.
- `decisions`: design decision register copied from `design_report.decision_register`.
- `metrics`: selected-candidate evaluation copied from `design_report.candidate_evaluation`.

LLM boundary:
- The LLM may interpret the objective, explain the hypothesis, and review risk/strategy notes.
- The LLM must not be the final optimizer, must not directly create STL vertices, and must not override hard constraints.
- Candidate generation, constraint filtering, scoring, repair fallback, and selection remain deterministic/statistical code paths.

`design_report.v1` required structure:
- `hypothesis`: statement, variables_under_test, expected_tradeoffs, falsification_signal.
- `objective`: experiment_objective.v1 with primary_metric, direction, secondary_metrics, constraints, success_criteria, and stop_criteria.
- `prior_context`: prior_count, best_prior, knowledge_summary, bo_recommendation, failure_memory.
- `candidate_generation`: strategy, budget, design_space, candidate_count, valid_count, rejected_count, repaired_count, candidate_ledger, top_candidates.
- `candidate_evaluation`: selected_candidate_id, selected_score, predicted_objective, uncertainty, manufacturability_score, information_gain_score, risk_score, constraint_margin_score.
- `rejected_candidates`: candidate_id, candidate_fingerprint, geometry_type, reason, reasons, repair_attempted, repair_result, status.
- `repaired_candidates`: any conservative fallback candidates created after hard constraint rejection.
- `manufacturability`: printer/material/FDM summary and warnings.
- `decision_register`: objective normalization, constraint gate, candidate selection, and handoff readiness decisions.
- `handoff_to_specimen`: required_fields_present, missing_required_fields, manufacturing_notes, known_risks, authoritative_specimen_id, authoritative_candidate_id.

Feedback inputs:
- KnowledgeAgent context is read from `state.run_metadata["knowledge"]` and summarized under `design_report.prior_context.knowledge_summary`.
- BOAgent output is read from `state.run_metadata["bo_agent"]` and `state.run_metadata["bo_recommended_constraints"]` and summarized under `design_report.prior_context.bo_recommendation`.
- Failure memory is read through `ctx.failure_memory.recent(...)` and summarized under `design_report.prior_context.failure_memory`.
- Experiment history is read through `ctx.experiment_db.list_recent(...)` and summarized under `design_report.prior_context.best_prior`.

Runtime state persistence:
- `LangGraphRunLoop._merge_agent_data` stores each stage payload under `state.run_metadata["<stage>_agent_payload"]`.
- Design reports are additionally stored under `state.run_metadata["design_report"]` and handoff packets under `state.run_metadata["design_candidate"]` / `state.run_metadata["design_handoff_packet"]`.

Live GUI/report behavior:

2026-05-29 Update: Specimen Making Autonomous Fabrication Loop
============================================================

SpecimenMakingAgent is now a fabrication-execution planning agent, not only an STL/printer.prepare caller. The existing tool chain remains unchanged and safe:

experiment_spec -> geometry.generate_metamaterial_stl -> geometry.check_mesh_quality -> geometry.check_manufacturability -> artifact.create_specimen_handoff -> experiment.evaluate -> printer.prepare

The new contract preserves the existing `specimen_result` and `protocol_note`, and adds structured manufacturing evidence:

- `fabrication_report`: `fabrication_report.v1` reportable manufacturing record.
- `specimen_fabricated`: `specimen_fabricated.v1` downstream handoff packet. It carries `fabrication_report_ref` and a compact `fabrication_summary`; the full report stays in `fabrication_report` / `state.run_metadata.fabrication_report` to avoid duplicating large runtime payloads.
- `handoff_packet`: same specimen handoff packet for generic runtime packet registry.
- `decisions`: manufacturing decision register.
- `metrics`: quality-gate and process-plan metrics.
- `evidence_refs`: STL, G-code, and handoff package references.

`fabrication_report.v1` sections:

- `fabrication_intent`: mode, printer path, physical intent, live-gui-test flag, specimen purpose.
- `digital_thread`: candidate/specimen ids, design hash, geometry hash, STL path, G-code path, remote G-code path, handoff package path, printer profile, material, graph/run ids, printer job id when available.
- `process_plan`: layer height, first-layer height, nozzle, bed temperatures, adhesion policy, cap-skin policy, ejection policy, estimated mass/time, slicer command.
- `quality_gates`: required fields, geometry, mesh, manufacturability, slicer, G-code, printer storage, execution gate, and ejection gate with pass/warn/fail/blocked status.
- `monitoring_plan`: PrusaLink status, transfer-idle check, after-print camera handoff, explicit `layerwise_monitoring_available=false`, defect classes for future Vision/quality loops.
- `printer_runtime`: printer.prepare status, mode/path, step_trace, upload/transfer/start/ejection summaries, operator messages.
- `fabrication_outcome`: ready/virtual/blocked/failed status, expected location, warnings, failure code, after-print confirmation requirement.
- `feedback_to_design`: do-not-repeat gates, recommended parameter adjustments, quality score, uncertainty.

Safety boundaries:

- `printer.prepare` remains the only printer boundary. Do not add a direct printer-control path inside SpecimenMakingAgent.
- The LLM may summarize intent, explain process reasoning, and suggest repair actions. It must not generate or patch G-code directly.
- Live physical action requires existing printer bridge gates, explicit operator/Live GUI intent, and Guardian/runtime safety checks.
- Active layer-wise defect correction, pause/cancel/retry, and auto corrective G-code changes are not enabled by this contract. They remain future extensions unless Guardian/operator gates are added.

Live GUI behavior:

- Specimen report title: `Manufacturing Digital Thread / Printer Runtime`.
- Specimen chat/runtime card shows Fabrication Digital Thread before PrusaSlicer/PrusaLink details.
- Specimen report must show Fabrication Intent, Digital Thread, Process Plan, Quality Gates, Printer Runtime, Monitoring/Feedback, and Handoff Packet.
- Live GUI selected Specimen report presents these fields as generic 3DP cards: Build Intent, Printer Telemetry, Readiness Gate, Slice Profile, Thermal / Material, Transfer Queue, central Live Job Monitor, Layer Preview, Camera Evidence, Post-Print Automation, G-code Validation, and Handoff / Artifacts. The Live Job Monitor is the only full-width focus card and must read backend evidence rather than fabricating progress.
- STL visual preview remains Design Agent territory. Specimen Agent surfaces manufacturing runtime visibility: slicer settings, G-code path, PrusaLink storage/readiness, upload/start/transfer/ejection, step trace, and handoff readiness.

Runtime persistence:

- `RunLoop._merge_agent_data` and `MainController._merge_planning_agent_data` preserve `fabrication_report`, `specimen_fabricated`, `specimen_handoff_packet`, `specimen_decision_register`, and `specimen_metrics` under `state.run_metadata`.
- `handoff_packets` receives the `specimen_fabricated.v1` packet, so Vision/Manipulation/Knowledge/BO can consume the same manufacturing evidence.

Completion semantics:

- Specimen stage completion means a fabrication digital thread and inspection-ready handoff exists. It does not mean that a physical print has necessarily completed unless `fabrication_outcome.status` and printer runtime evidence prove it.
