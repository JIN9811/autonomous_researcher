# Vision Pickup Observation Runtime Guideline

Status: implementation guideline
Last reviewed: 2026-05-24
Scope: Vision Agent observation contract between Specimen Making and Manipulation.

## 1. Purpose

Vision Agent performs a lightweight pickup-area observation after the Specimen
Making Agent finishes 3DP preparation or printing.

The goal is not full scene understanding. The goal is to provide the
Manipulation Agent with a stable, typed observation for the 3DP output area:

- whether a camera capture succeeded
- whether the pickup area is anomalous
- the approximate specimen pickup pose
- whether the printed specimen is ready for robot transfer
- the source and target locations for the following manipulation stage

## 2. Pipeline Position

The runtime stage order remains:

```text
Design -> Specimen Making -> Vision -> Manipulation -> Lab Equipment -> Analysis -> Knowledge -> Guardian
```

Vision remains between Specimen Making and Manipulation so robot policy rollout
does not bypass the latest observation.

## 3. Tool Contract

Vision Agent calls:

```text
camera.capture
lerobot.active_robot_cam.capture  # wrist active-cam one-shot evidence
lerobot.camera.test               # optional camera diagnostics
```

Minimum request:

```json
{
  "frame_id": "frame-0-vision",
  "camera_key": "top",
  "purpose": "3dp_output_pickup_check",
  "specimen_id": "specimen-id"
}
```

Minimum tool response:

```json
{
  "ok": true,
  "tool": "camera.capture",
  "frame_id": "frame-0-vision",
  "camera_key": "top",
  "source": "simulator",
  "anomaly": false
}
```

Live camera bridges may add image paths, measured pose fields, confidence, or
camera-specific metadata. The agent must tolerate absent optional fields.

When the LeRobot active-camera bridge is available, Vision Agent calls
`lerobot.active_robot_cam.capture` once after the Specimen Making / printer
autoejection handoff. The default active camera key is `wrist`; experiment specs
may override it with `active_cam_camera_key`, `vision_active_camera_key`, or
`active_robot_cam_primary_camera_key`. This Live GUI one-shot route temporarily
owns the saved camera port while the follower moves to the capture pose, records
one frame, and returns to its resume pose. It is distinct from the parallel
Active Cam observer embedded in teleoperation/recording sessions.

The one-shot bridge isolates camera ownership in a child process. A successful
child exit closes all camera handles at the operating-system boundary and may
produce `port_released=true`, `camera_returned_to_vla=true`,
`camera_owner_after=vla_runtime`, and `release_status=process_exit_verified`.
The bridge must not reopen RGB-D merely to prove release because doing so races
with the next Manipulation/VLA rollout owner. Routine presence and USB-link
checks use Linux sysfs without opening an SDK context; the rollout performs the
next actual stream acquisition. This lease rule does not alter or restart the
teleoperation/recording parallel observer.

Some D455F USB 2.0 enumerations expose the product/model and link speed in
sysfs but leave the USB serial field empty. The bridge keeps that device visible
through the configured `top` identity, reports the 480 Mbps rollout warning,
and still does not open an SDK context merely to recover the serial.

When the previous Manipulation result requests post-place Vision verification,
Vision Agent must switch to the UTM verification path instead of running the
active-camera ejection check again. In that path `camera.capture` uses
`purpose=utm_placement_verification` and `camera_key=utm` unless overridden by
`utm_camera_key` / `vision_utm_camera_key`. The resulting
`vision_manipulation_completion.v1` signal is consumed by Manipulation Agent to
stop the existing rollout and complete the handoff.

## 5. Test Mode

Test mode uses the deterministic `camera.capture` mock and the latest
`run_metadata.specimen_result`.

Expected behavior:

- if `specimen_result.ok` is not false and no operator input is pending,
  `transfer_readiness.ready=true`
- if capture fails or anomaly is true, `transfer_readiness.ready=false`
- no real camera or robot process is launched by Vision Agent itself

## 6. Live Mode

Live mode keeps the same contract, but the camera tool may use saved top/wrist
camera identities from the LeRobot workspace.

Vision Agent still only observes. It must not start robot rollout, printer jobs,
or UTM equipment.

## 7. Downstream Use

Manipulation Agent consumes:

- `state.latest_observations.pose_estimate`
- `state.latest_observations.pickup_target`
- `state.latest_observations.transfer_readiness`
- `state.latest_observations.anomaly`

The Manipulation Agent may block, reduce confidence, or request recovery when
`transfer_readiness.ready=false` or `anomaly=true`.

## 2026-05-29 Vision Agent Lab Perception Signal Loop Update

This guideline is upgraded from a lightweight pickup observation contract to the
`vision_report.v1` / `vision_signal.v1` lab perception signal contract described
in `개선안/03_vision_agent_lab_perception_signal_loop_research.md`.

The legacy downstream keys remain authoritative for compatibility:

- `observation.pose_estimate`
- `observation.pickup_target`
- `observation.transfer_readiness`
- `observation.anomaly`
- `protocol_note`

New runtime outputs:

- `vision_report`: `vision_report.v1` human/report-facing perception record.
- `vision_signal`: `vision_signal.v1` downstream handoff packet and signal bus record.
- `handoff_packet`: same `vision_signal.v1` packet for the generic runtime packet registry.
- `decisions`: task resolve, capture acceptance, signal arbitration, and handoff-readiness decisions.
- `metrics`: zone/detection/signal counts, confidence range, transfer readiness, anomaly state, freshness TTL.
- `evidence_refs`: annotated scene SVG and detection JSON evidence paths.

`vision_report.v1` sections:

- `task`: post-ejection, pickup, UTM fixture, reset, or other observation objective.
- `model_backend`: simulator/rule backend now, optional DINOv3/Grounding-DINO/SAM2/FoundationPose metadata later.
- `camera_source`: camera key, source, frame id, timestamp, calibration id, frame age.
- `scene_map` / `zones`: printer bed, ejection basket, robot workspace, robot gripper, UTM platen, UTM screen state.
- `detections`: label, zone, bbox/mask path when available, confidence, source.
- `events`: visual transition events such as `printer_bed_clear`, `specimen_ejected_to_basket`, `basket_contains_specimen`, or `anomaly_detected`.
- `signal_board` / `agent_signals`: freshness-bounded signals including `printer_output_visible`, `specimen_ejected_to_basket`, `spc_autoejection_confirmed`, `basket_contains_specimen`, `pickup_ready`, `basket_empty_after_pick`, `gripper_holding_specimen`, `specimen_on_utm_platen`, `fixture_alignment_ok`, `utm_motion_observed`, `utm_home_restored`, `equipment_screen_state`, `robot_workspace_clear`, `visual_test_evidence_ready`, `data_quality_low`, and `anomaly_detected`. Signals that are outside the current observation stage are emitted as `not_checked` rather than silently omitted.
- `artifacts`: raw frame path when supplied, active-camera ejection capture path when supplied, generated annotated scene SVG, detection JSON, before/after path when supplied.
- `dataset_ledger`: LeRobot/data-reuse metadata for future policy improvement.
- `knowledge_payload`: success/failure labels and visual notes for Knowledge Agent memory.
- `cross_agent_contract`: explicit statement that Vision observes only and downstream agents execute actions.
- `freshness_policy`: signal TTL and stale-signal blocking rule.

`vision_signal.v1` required freshness fields:

- `signal_id`
- `zone_id`
- `value`
- `confidence`
- `stable_for_ms`
- `timestamp`
- `expires_at`
- `consumer_agents`
- `evidence_refs`

Downstream invariant:

- Manipulation must not use an expired Vision signal. Current `ManipulationAgent`
  checks `transfer_readiness.expires_at` / `vision_signal.expires_at` and blocks
  with `failure_code=STALE_VISION_SIGNAL` when the signal is stale or malformed.
- Equipment and future cross-check handlers must follow the same rule when UTM,
  screen, or fixture signals become live action preconditions.

Safety boundary:

- Vision Agent never starts robot rollout, printer jobs, UTM commands, or
  PyAutoGUI actions. It only emits `vision_signal.v1` and visual evidence.
- If confidence is low, the camera fails, or anomaly is detected, the signal board
  must expose a blocking reason and Guardian/operator review path.

Current implementation scope:

- Test mode and camera unavailable paths use deterministic simulator/rule output.
- When the LeRobot bridge is available, test mode can attach `/api/lerobot/camera/test` frame evidence; live mode requires explicit camera/live confirmation before any camera test is called.
- Active-camera ejection confirmation is represented by
  `active_cam_ejection_check.v1`, `spc_autoejection_confirmation.v1`, and the
  `spc_autoejection_confirmed` signal targeted at `specimen_agent`. This is the
  visual completion signal for printer-side autoejection. It does not authorize
  Manipulation Agent rollout by itself; Manipulation still consumes
  `pickup_ready` and pose freshness.
- The current `camera.capture` registration remains a deterministic typed
  observation tool. It should not be documented as directly opening RealSense or
  webcam streams in the main closed-loop path.
- `device_bridges/realsense_bridge.py` is available as a guarded bridge class
  for RealSense enumeration, profile validation, and single-frame capture. It is
  intentionally fail-closed: enumeration and profile validation do not start
  streams, and capture requires `allow_stream=true` or
  `live_stream_confirmed=true` plus an advertised stream profile. It is not yet
  exposed as a dedicated FastAPI workspace page/API.
- DINOv3/Grounding DINO/SAM2/FoundationPose are represented as optional backend
  metadata, not assumed live dependencies.
- The runtime writes Vision evidence artifacts and registers nested visual
  evidence paths in the event/artifact stream.

Active Cam run-artifact lifecycle:

- A confirmed Active Cam frame is copied from the transient camera runtime path
  into `runs/<run_id>/vision/<observation_id>/active_cam_capture_<timestamp>.*`.
  The copied file, not the transient `/tmp` path, is the canonical loop artifact.
- Vision emits `active_cam_artifact_update` with schema
  `active_cam_run_artifact.v1`; both LangGraph and Live GUI handoff paths store
  the successful descriptor as `run_metadata.latest_active_cam_artifact`.
- Later agent handoffs that do not perform an Active Cam attempt preserve that
  pointer, so the frame remains visible until another Active Cam attempt ends.
- A later confirmed capture replaces the pointer. An explicit failed, blocked,
  or error result clears only the current display pointer and does not delete
  immutable Active Cam artifacts from earlier observations.
- The Live GUI reads the canonical `/api/runs/<run_id>/artifact-file/...` URL.
  It must not use Base64/session-only state as the persistence mechanism.

Live GUI chat message contract:

- Planning/runtime Vision completion messages should be emitted as
  `live_chat_message.v1` with `message_type=signal` when the planning loop is
  driving the workflow.
- The human-readable content must include camera source, zone-state summary,
  primary `pickup_ready` status/confidence, `expires_at`, anomaly state, and at
  least one visual evidence path when available.
- The structured message payload should carry `signal_id`, `zone_id`,
  `confidence`, `stability_ms`, `vision_report`, `vision_signal`, and
  `agent_signals` so the Live GUI chat and report view stay consistent.

## Active Cam Autoejection Confirmation

After 3DP auto-ejection, VisionAgent uses the configured LeRobot wrist Active Cam routine to capture one confirmation frame. The same routine includes the robot capture pose and returns the camera port to the VLA runtime before ManipulationAgent starts inference. No separate pose-camera path is part of this route.

Required readiness fields:

```json
{
  "spc_autoejection_confirmed": true,
  "camera_returned_to_vla": true,
  "vla_camera_precheck_ok": true
}
```

Live mode blocks ManipulationAgent when the Active Cam frame is missing, specimen confirmation fails, or the camera port is not returned to the VLA route. Test mode uses the same contract with deterministic bridge evidence; it must not introduce a separate pose-camera path.
