BO Agent Runtime Guideline

Purpose
- BO Agent is the optimization scientist in the Autonomous Researcher closed loop.
- It does not fabricate specimens, slice G-code, move robots, run UTM equipment, or override Guardian.
- It reads measured evidence, Knowledge memory, failure patterns, and operator BO settings, then recommends the next Design Agent constraints.
- LLM reasoning is visible and auditable, but it is only a soft preference layer. Numeric acquisition, schema/range checks, failure memory, and downstream manufacturability validation decide the final candidate.

External reference scope
- Reference repository: https://github.com/sparks-baird/self-driving-lab-demo
- Reused concepts only:
  - standard experiment objective/evaluation interface
  - random/grid/BO comparison
  - best-so-far trace
  - operator-readable optimization tutorial/report style
- Do not import the reference project as a dependency.
- Do not copy optics/RGB/MQTT/cloud demo code.

Runtime identity
- User-facing page: BO Workspace
- Route: /bo
- Agent name: bo_agent
- Module: graphs/modules/bo/module.yaml
- LLM task route: bo_policy
- Runtime tool path: experiment.benchmark
- Primary result key: bo_result
- State metadata key: run_metadata["bo_agent"]
- Next-design state key: run_metadata["bo_recommended_constraints"]
- Next-design handoff key: run_metadata["next_design_request"]

Closed-loop position
- Default closed loop:
  design -> specimen -> vision -> manipulation -> equipment -> analysis -> knowledge -> bo -> guardian -> design|complete|error
- BO consumes Analysis/Knowledge results and proposes the next Design constraints.
- Guardian still performs final loop decision and safety/consistency review.

Core responsibilities
1. Normalize objective and parameter space.
2. Lock operator-controlled/test-option parameters, especially cell_size_mm.
3. Ingest Analysis bo_handoff / bo_observation / experiment_evaluation before generic priors.
4. Separate failed priors into failure_model instead of successful BO observations.
5. Ask the LLM for strict JSON reasoning when llm_preference_enabled=true.
6. Sanitize LLM JSON into bo_reasoning_v1.
7. Run experiment.benchmark with random/grid/bo-compatible strategy values.
8. Build and rank candidate_pool using numeric acquisition + LLM preference - risk/constraint penalties.
9. Write auditable artifacts.
10. Emit next_design_request.v1 for Design Agent.

Benchmark backend mapping
- experiment.benchmark currently supports random, grid, bo strategy payloads.
- Higher-level reasoning strategies map to the bo benchmark strategy:
  - llm_warmstart -> bo
  - llm_preference_bo -> bo
  - safe_constrained_bo -> bo
  - multi_objective_pareto -> bo
  - multi_fidelity_bo -> bo
- The original requested strategy is preserved in bo_result.strategy.
- The actual benchmark strategy is stored in bo_result.benchmark_strategy.

Numeric backend options
- lightweight_pool
  - Default. No heavy dependency.
  - Uses deterministic candidate-pool proxy mean, uncertainty, and acquisition formulas.
- botorch_optional
  - Default dependency. Installed through requirements.txt / pyproject default dependencies.
  - Uses BoTorch SingleTaskGP posterior scoring over the existing candidate pool.
  - Keeps categorical/boolean/fixed manufacturing variables inside the repository candidate-pool and validator contract.
  - Does not run unconstrained continuous optimize_acqf by default.
  - If torch/botorch/gpytorch import fails, data is insufficient, or GP fitting fails, it falls back to lightweight_pool and records backend_warnings.

Backend result fields
- bo_result.bo_backend: requested numeric backend from operator/API.
- bo_result.benchmark.bo_backend_requested: requested backend passed to experiment.benchmark.
- bo_result.benchmark.backend_warnings: global backend fallback warnings.
- bo_result.benchmark.strategies.bo.backend_requested: requested backend for bo strategy.
- bo_result.benchmark.strategies.bo.backend_active: actual backend used for at least one BO step, usually lightweight_pool or botorch_optional.
- bo_result.benchmark.strategies.bo.surrogate_trace[*].backend_active: backend used for that specific step.

Default parameter space
- geometry_type: ["gyroid"]
- relative_density: [0.20, 0.48]
- wall_thickness_mm: [1.2, 2.0]
- cell_size_mm: [5.0, 10.0]
- tpms_thickness: [0.28, 0.52]
- orientation_deg: [0, 15, 30, 45, 60, 90]
- anisotropy_ratio: [0.85, 1.0, 1.25]
- skin_thickness_mm: [0.0, 0.8]
- bottom_cap_enabled: [true]
- top_cap_enabled: [false]
- skirt_enabled: [false]

Loop-stable parameters
- cell_size_mm is operator/test-option controlled.
- If current_experiment_spec.cell_size_mm or current_experiment_spec.constraints.cell_size_mm exists, BO must lock benchmark and recommendation to that value.
- BO may recommend relative_density, wall_thickness_mm, tpms_thickness, orientation_deg, anisotropy_ratio, cap flags, skirt flags, and preferred geometry.
- BO must not silently change saved/test-selected cell size between cycles.
- For gyroid TPMS, relative_density < 0.20 is invalid for FDM continuous-shell generation.

Failed prior rule
- ok_for_bo=false, failure_tags, failed/blocked status, missing parameter vector, or poor quality gates must not be treated as successful BO observations.
- Failed priors feed failure_model.risk_patterns and forbidden_regions.
- Failure data must be preserved, not discarded.

LLM reasoning contract
- Task route: bo_policy
- Prompt registry entry: backends/prompt_registry.py -> bo_policy
- Model route: configs/models.yaml -> bo_policy
- LLM output must be strict JSON. Free prose is rejected and deterministic fallback reasoning is used.
- Required schema: bo_reasoning_v1

LLM output keys
- schema_version
- hypotheses
- strategy_recommendation
- search_space_patch
- preference_regions
- risk_flags
- operator_summary

LLM may do
- Interpret objective and constraints.
- Summarize evidence/failure patterns.
- Propose hypotheses.
- Suggest search-space narrow/expand/lock/forbid operations.
- Suggest acquisition/exploration/exploitation direction.
- Provide preference regions and operator-facing rationale.

LLM must not do
- Execute hardware.
- Invent unsupported parameter keys.
- Override numeric acquisition or validators.
- Override measured evidence with intuition.
- Bypass Guardian or manufacturability validation.
- Write raw objective_score.

Candidate scoring
combined_score =
  normalized_numeric_acquisition_score
  + llm_weight * llm_preference_score
  - failure_risk_penalty
  - constraint_violation_penalty
  - duplicate_penalty

Default llm_weight policy
- If llm_candidate_weight is numeric, clamp to [0.0, 0.45].
- If llm_candidate_weight="auto":
  - prior_count/loop_count <= 3: 0.25
  - <= 10: 0.15
  - > 10: 0.08
- As real measured evidence grows, LLM influence decreases.

Condition grammar for LLM preference/risk regions
- Numeric range: relative_density between 0.30 and 0.42
- Numeric comparison: wall_thickness_mm >= 1.2
- Boolean equality: bottom_cap_enabled = true
- String equality: geometry_type = gyroid
- Multiple clauses: condition A and condition B, or A && B

Mode behavior
- Test mode:
  - No physical hardware.
  - execution.mode=virtual and bridge=virtual.
  - Deterministic for fixed seed.
- Live mode:
  - BO Agent itself still evaluates virtually unless a future explicit live experiment API is added.
  - Physical execution remains downstream through Design, Specimen Making, Vision, Manipulation, Equipment, Analysis, Guardian.
- Live GUI:
  - BO chat card displays strategy, acquisition, prior counts, recommendation, reasoning summary, and candidate ranking.
  - Heavy surrogate plots remain collapsible to avoid DOM/memory growth.

Design Agent consumption rule
- Design Agent may read run_metadata["bo_recommended_constraints"] or run_metadata["next_design_request"].
- It must run its own manufacturability and schema validation again.
- BO recommendation is a next experiment candidate, not fabrication approval.
- cell_size_mm must remain operator/test-option authoritative.

Validation requirements
- Unit tests:
  - BO Agent returns valid bo_result.
  - normalize_settings fallback works.
  - MBO without priors degrades safely.
  - cell_size lock is preserved.
  - prior/current specimen is penalized to avoid repeat recommendations.
  - bo_result emits reasoning, candidate ranking, next_design_request, and artifacts.
  - LLM preference regions affect ranking as a soft score.
- Integration tests:
  - /api/bo/config reports defaults and persists saved settings.
  - /api/bo/benchmark runs virtual BO and emits workspace events.
  - Higher-level reasoning strategies map to bo backend for benchmark.
  - /api/bo/run returns recommendation and artifacts.

Failure behavior
- Unknown strategy falls back to bo with warning.
- Unknown acquisition falls back to expected_improvement with warning.
- Empty/invalid budget coerces to at least 1.
- Missing prior evaluations in MBO degrades to BO with warning.
- Non-JSON or failed LLM reasoning uses deterministic fallback and records a warning.
- Invalid/failure-prone LLM preference regions only add risk/penalty; they do not force a candidate.
- botorch_optional import/fit failure falls back to lightweight_pool and records backend_warnings.
- If no valid recommendation exists, next_design_request.status becomes blocked.
