BO Agent Runtime Guideline

Purpose
- BO Agent is the optimization scientist in the Autonomous Researcher closed loop.
- It does not fabricate specimens, slice G-code, move robots, run UTM equipment, or override Guardian.
- It reads measured evidence, Knowledge memory, failure patterns, and operator BO settings, then recommends the next Design Agent constraints.
- LLM reasoning is visible and auditable, but it is only a soft preference layer. Numeric acquisition, schema/range checks, failure memory, and downstream manufacturability validation decide the final candidate.

External reference scope
- Reference repository: https://github.com/sparks-baird/self-driving-lab-demo
- Reused concepts only:
  - standard experiment objective/evaluation interface
  - random/grid/BO comparison
  - best-so-far trace
  - operator-readable optimization tutorial/report style
- Do not import the reference project as a dependency.
- Do not copy optics/RGB/MQTT/cloud demo code.

Compiled objective contract
- The operator starts with research intent, not a fixed objective template.
- The LLM may compose or revise one objective_spec.v1 JSON document, but that
  output is untrusted until deterministic validation succeeds.
- The operator may instead author the same contract through Visual Builder or
  Advanced JSON. These are authoring surfaces, not alternate runtime formats.
- Required lifecycle: draft -> validate -> preview -> operator approve ->
  activate for run_id.
- Activation binds objective_id, version, and canonical objective_hash
  immutably to the run.
- Analysis is the only runtime stage that evaluates the bound expression from
  registered metrics. BO consumes the resulting objective_evaluation.v1.
- BO must not call the LLM to recalculate an existing score.

Manual objective authoring
- Route: /bo -> Bounded Objective Compiler.
- Modes: AI Compose, Visual Builder, Advanced JSON.
- Visual Builder reads GET /api/objectives/authoring-contract. Do not hardcode a
  separate frontend operator list, unit list, AST depth, or AST node limit.
- The authoring contract is derived from the deterministic compiler. Disabled
  operators such as reference remain visible to contract inspection but cannot
  be selected or accepted.
- The visual tree supports registered metric and literal leaves, unary and
  variadic expressions, named binary slots, weighted terms, aggregates,
  conditions, comparisons, Boolean constraints, and piecewise penalty points.
- Compatible subtrees may be reordered, duplicated, deleted, or reparented.
  These operations only mutate the unsaved browser draft.
- Visual Builder and Advanced JSON share one canonical last-valid spec.
- Invalid JSON must remain visible with path-specific errors. It must not
  replace the last valid visual tree or silently revert to a different draft.
- Restore Last Valid discards only the invalid JSON buffer and redraws the
  canonical visual tree.
- Unsaved manual work may be retained in browser storage across refresh. A
  successful server save clears that recovery state.
- Selecting Objective Version changes the read-only lifecycle inspection only.
  It must never overwrite the manual draft automatically.
- Load Selected as Revision is the explicit operation that copies a stored
  version into the manual builder and records its parent identity.
- POST /api/objectives/manual accepts spec, operator, and optional revision_of.
  The server assigns lifecycle=draft, created_by=operator:<name>, timestamp,
  Metric Registry version, and immutable version. Client-supplied values for
  those fields are not authoritative.
- Creating an existing objective_id without revision_of is a conflict. A
  revision must use the same objective_id and the next immutable version.
- A saved manual draft is not executable. Validate, observation Preview,
  operator Approve, and Activate for one run_id remain mandatory.
- Manual authoring never executes Python, JavaScript, shell, filesystem,
  network, Cypher, or arbitrary code supplied in the objective document.

Closed-loop position
- Default closed loop:
  design -> specimen -> vision -> manipulation -> equipment -> analysis -> knowledge -> bo -> guardian -> design|complete|error
- BO consumes Analysis/Knowledge results and proposes the next Design constraints.
- Guardian still performs final loop decision and safety/consistency review.

Core responsibilities
1. Normalize objective and parameter space.
2. Keep exactly two Gyroid BO variables active: cell_size_mm and relative_density; lock unrelated geometry/process settings.
3. Ingest Analysis bo_handoff / bo_observation / experiment_evaluation before generic priors.
4. Separate failed priors into failure_model instead of successful BO observations.
5. Ask the LLM for strict JSON reasoning when llm_preference_enabled=true.
6. Sanitize LLM JSON into bo_reasoning_v1.
7. Use deterministic Latin Hypercube initial design until the configured observation target is complete.
8. Fit SingleTaskGP and optimize one acquisition point with optimize_acqf or optimize_acqf_mixed.
9. Write auditable artifacts.
10. Emit next_design_request.v1 for Design Agent.

Benchmark backend mapping
- experiment.benchmark currently supports random, grid, bo strategy payloads.
- Higher-level reasoning strategies map to the bo benchmark strategy:
  - llm_warmstart -> bo
  - llm_preference_bo -> bo
  - safe_constrained_bo -> bo
  - multi_objective_pareto -> bo
  - multi_fidelity_bo -> bo
- The original requested strategy is preserved in bo_result.strategy.
- The actual benchmark strategy is stored in bo_result.benchmark_strategy.

Numeric backend options
- botorch
  - Default production backend. Installed through requirements.txt / pyproject default dependencies.
  - Uses a normalized mixed parameter codec, BoTorch SingleTaskGP, and direct acquisition optimization.
  - Uses optimize_acqf for continuous spaces and optimize_acqf_mixed for enumerated discrete choices.
  - Uses Latin Hypercube initial design before enough accepted observations exist.
  - A fit/import/optimizer failure is typed and blocks that BO result; it never silently changes the requested backend.
- lightweight_pool
  - Explicit comparison/debug backend only.
  - Uses deterministic candidate-pool proxy mean, uncertainty, and acquisition formulas.
- botorch_optional
  - Legacy saved-setting alias only. It is normalized to botorch before execution.

Initial design and optimizer defaults
- initial_sampler: latin_hypercube
- initial_design_size: 8 valid measured observations for the canonical two-variable Gyroid problem
- The standard 20-cycle mission allocates cycles 1-8 to Latin Hypercube
  initialization and cycles 9-20 to SingleTaskGP + Expected Improvement when
  every observation is accepted. Rejected, infeasible, proxy-only, or
  missing-SEA records do not advance the eight-observation initialization count.
- acquisition: expected_improvement, implemented with LogExpectedImprovement
- num_restarts: 12
- raw_samples: 256
- optimizer_timeout_s: 30
- A closed-loop BO Agent call emits exactly one next point. A BO Workspace benchmark may evaluate its requested synthetic budget.

Backend result fields
- bo_result.bo_backend: requested numeric backend from operator/API.
- bo_result.benchmark.bo_backend_requested: requested backend passed to experiment.benchmark.
- bo_result.benchmark.backend_warnings: backend diagnostics; never evidence of a silent backend downgrade.
- bo_result.benchmark.strategies.bo.backend_requested: requested backend for bo strategy.

Default parameter space
- geometry_type: ["gyroid"]
- relative_density: [0.20, 0.48]
- cell_size_mm: [5.0, 6.0, 7.5, 10.0], derived from a=L/N with L=30 mm and N={6,5,4,3}
- wall_thickness_mm: [1.2]
- tpms_thickness: [0.0], solved by the TPMS generator to realize relative_density
- orientation_deg: [0.0]
- anisotropy_ratio: [1.0]
- skin_thickness_mm: [0.8]
- bottom_cap_enabled: [true]
- top_cap_enabled: [false]
- skirt_enabled: [false]

Loop-stable parameters
- cell_size_mm and relative_density are the only active BO variables in the canonical Gyroid problem.
- cell_size_mm must remain in the feasible discrete set derived from a=L/N; it is not treated as a static test-option lock during a multi-cycle BO run.
- geometry_type, specimen envelope, orientation_deg, anisotropy_ratio, cap flags, skirt flag, and process settings remain fixed unless a different approved parameter-space contract is loaded.
- The first design in a multi-cycle test workflow is seeded from the same deterministic eight-point LHS sequence used by BO Agent. Orchestrator publishes that point in `orchestrator_design_contract.v1` before Design Agent runs; later BO requests are republished through the same Orchestrator contract and consume the next unobserved point until the initial-design target is complete.
- For gyroid TPMS, relative_density < 0.20 is invalid for FDM continuous-shell generation.

Failed prior rule
- ok_for_bo=false, failure_tags, failed/blocked status, missing parameter vector, or poor quality gates must not be treated as successful BO observations.
- Failed priors feed failure_model.risk_patterns and forbidden_regions.
- Failure data must be preserved, not discarded.
- Duplicate Analysis packets with the same observation_id count as one
  observation even when both bo_handoff and bo_observation are present.
- Live mode rejects synthetic or simulation proxy scores. Test mode accepts
  only explicitly labelled synthetic/simulation fidelity.

LLM may do
- Interpret objective and constraints.
- Summarize evidence/failure patterns.
- Propose hypotheses.
- Suggest search-space narrow/expand/lock/forbid operations.
- Suggest acquisition/exploration/exploitation direction.
- Provide preference regions and operator-facing rationale.

LLM must not do
- Execute hardware.
- Invent unsupported parameter keys.
- Override numeric acquisition or validators.
- Override measured evidence with intuition.
- Bypass Guardian or manufacturability validation.
- Write raw objective_score.

Candidate scoring
combined_score =
  normalized_numeric_acquisition_score
  + llm_weight * llm_preference_score
  - failure_risk_penalty
  - constraint_violation_penalty
  - duplicate_penalty

Default llm_weight policy
- If llm_candidate_weight is numeric, clamp to [0.0, 0.45].
- If llm_candidate_weight="auto":
  - prior_count/loop_count <= 3: 0.25
  - <= 10: 0.15
  - > 10: 0.08
- As real measured evidence grows, LLM influence decreases.

Condition grammar for LLM preference/risk regions
- Numeric range: relative_density between 0.30 and 0.42
- Numeric comparison: wall_thickness_mm >= 1.2
- Boolean equality: bottom_cap_enabled = true
- String equality: geometry_type = gyroid
- Multiple clauses: condition A and condition B, or A && B

Mode behavior
- Test mode:
  - No physical hardware.
  - execution.mode=virtual and bridge=virtual.
  - Deterministic for fixed seed.
- Live mode:
  - BO Agent itself still evaluates virtually unless a future explicit live experiment API is added.
  - Physical execution remains downstream through Design, Specimen Making, Vision, Manipulation, Equipment, Analysis, Guardian.
- Live GUI:
  - During initial design, the BO chat/report cards display Latin Hypercube progress, next point, backend=lhs, and selected parameters.
  - During initial design, candidate ranking, combined score, acquisition score, and LLM preference reranking are disabled.
  - After eight accepted measured observations, the cards switch to GP posterior, acquisition, reasoning audit, recommendation, and candidate ranking.
  - The posterior/EI figure is output-only: render scalar score, predictive uncertainty, measured scores, EI, and an anonymous normalized search coordinate. Never render cell_size_mm, relative_density, input values, parameter strata, parameter slices, or parameter tooltips in that figure. Input-space coordinates remain in the separate Design Agent LHS card and backend audit records.
  - Heavy surrogate plots remain collapsible to avoid DOM/memory growth.

Design Agent consumption rule
- Design Agent may read run_metadata["bo_recommended_constraints"] or run_metadata["next_design_request"].
- It must run its own manufacturability and schema validation again.
- BO recommendation is a next experiment candidate, not fabrication approval.
- Design Agent must preserve both BO-proposed cell_size_mm and relative_density after schema and manufacturability validation.

Validation requirements
- Unit tests:
  - BO Agent returns valid bo_result.
  - normalize_settings fallback works.
  - MBO without priors degrades safely.
  - both active variables are released from static closed-loop constraints and preserved from BO handoff.
  - prior/current specimen is penalized to avoid repeat recommendations.
  - bo_result emits reasoning, candidate ranking, next_design_request, and artifacts.
  - LLM preference regions affect ranking as a soft score.
- Integration tests:
  - /api/bo/config reports defaults and persists saved settings.
  - /api/bo/benchmark runs virtual BO and emits workspace events.
  - Higher-level reasoning strategies map to bo backend for benchmark.
  - /api/bo/run returns recommendation and artifacts.

Failure behavior
- Unknown strategy falls back to bo with warning.
- Unknown acquisition falls back to expected_improvement with warning.
- Empty/invalid budget coerces to at least 1.
- Missing prior evaluations in MBO degrades to BO with warning.
- Non-JSON or failed LLM reasoning uses deterministic fallback and records a warning.
- Invalid/failure-prone LLM preference regions only add risk/penalty; they do not force a candidate.
- BoTorch dependency, fit, or acquisition failure returns a BOTORCH_* failure and does not run lightweight_pool.
- If no valid recommendation exists, next_design_request.status becomes blocked.
