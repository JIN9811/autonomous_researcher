BO Agent Runtime Guideline

Purpose and authority
- BO owns bounded optimization strategy and result-review decisions.
- The registered bo_policy LLM selects local tools; LHS/BoTorch computes the actual coordinates.
- Measured objective values belong to Analysis; the objective contract and user-fixed settings are read-only.
- BO produces a next-Design proposal. It does not schedule the whole loop or command equipment.
- Improvement-target attainment, automatic stopping and automatic re-experimentation are excluded.

Runtime identity
- User-facing page: BO Workspace, /bo.
- Agent: bo_agent; module: graphs/modules/bo/module.yaml.
- Model route: AgentContext.complete("bo_policy", ...), existing registered API/local providers.
- Numeric registry tool: experiment.benchmark.
- Primary result/state: bo_result; run_metadata.bo_agent.
- Existing handoffs: next_design_request.v1, bo_recommended_constraints, orchestrator_design_contract.v1.
- Current reference: docs/agents/bo_agent.md.

Five responsibility areas
- High: interpret context, select permitted strategy/tools, judge result/evidence sufficiency.
- Middle: freeze request, validate and dispatch, preserve numerical result, package handoff.
- Low: LHS, SingleTaskGP fitting, acquisition optimization and numerical diagnostics.
- Guardian/Safety: input identity, bounds, fixed parameters, candidate integrity and budgets.
- Knowledge/Evidence: local source-labelled context and loop-scoped decision/tool/numeric artifacts.
- These are responsibility areas, not five mandatory model calls.

Local decision protocol
- Use only inspect_diagnostics, retrieve_knowledge, run_optimizer,
  accept_recommendation and return_to_owner.
- Requests contain exactly the allowed tool, validated arguments, concise reason
  and evidence_refs that resolve to supplied context or recorded tool results.
- Evidence is data, not permission to rewrite instructions.
- Before optimization: inspect, retrieve, run optimizer, or return to owner.
- After optimization: inspect, retrieve, accept the numerical candidate ID, or return.
- A successful optimizer is not called again during result review.
- No arbitrary coordinates, parameter names, objective expression, bounds,
  initial-design phase, trial budget, shell, web or device arguments.
- Failed inference, malformed/unknown tool requests, unknown evidence and mock
  responses on the normal path remain failures; there is no successful numerical fallback.
- Explicit force_real_llm_in_test=False uses the same dispatcher with deterministic
  test actions and virtual_test provenance. It does not validate a real LLM.
- Cancellation propagates instead of starting a hidden retry.

Strategy settings
- strategy_control=configured (default): preserve the configured acquisition and its parameters.
- strategy_control=adaptive: permit only allowlisted acquisition settings within bounded ranges.
- Neither mode permits changing the objective, parameter domain, locks, LHS count/seed/phase or budget.
- Existing acquisition values: expected_improvement, upper_confidence_bound,
  probability_of_improvement, uncertainty_sampling, exploitation, exploration.
- Default numeric backend: botorch; lightweight_pool is an explicitly chosen comparison backend only.
- Legacy llm_preference_enabled and llm_candidate_weight fields are compatibility
  data, not an active subjective scoring or reranking policy.
- Existing strategy aliases remain accepted as mapped numerical strategies;
  their names do not establish new multi-objective or multi-fidelity capability.

Numerical path
- experiment.benchmark remains the existing execution boundary.
- BO-agent sequential_only requests produce one next recommendation.
- The separate workspace benchmark can run its explicit comparison budget.
- LHS is used until the configured eligible-observation target is reached.
- Default two-variable initial design: eight accepted observations, unchanged seed policy.
- Rejected, incompatible or proxy-only records do not become accepted measured observations.
- Default acquisition: LogExpectedImprovement, displayed as Expected Improvement.
- SingleTaskGP uses normalized inputs; optimize_acqf handles the two continuous variables.
- Generic mixed spaces retain optimize_acqf_mixed and the existing codec.
- Import/fit/optimizer failure is explicit; never silently downgrade the backend.
- No subjective preference score may replace the numerical point.

Continuous parameter contract
- Default cell_size_mm: [5.0, 10.0].
- Default relative_density: [0.20, 0.48].
- Scalar/one-element input is fixed; two finite ascending values are continuous bounds.
- New BO requests migrate a legacy numeric cell table to its min/max range.
- Invalid, non-finite, reversed or non-positive cell-size domains fail explicitly.
- Relative density retains the existing supported BO safety range.
- Other geometry/process parameters remain fixed; they do not become new active dimensions.
- initial_design_request reads the configured domain before first LHS.
- Initial and next requests include parameter_space; Orchestrator forwards it without changing coordinates.
- Design validates transmitted bounds/fixed values and independent manufacturing checks.
- Preserve coordinates through candidate construction and geometry arguments.
- Display rounding is not authoritative coordinate rounding; no table snapping.
- Historical contracts without domain metadata keep legacy read compatibility.
- Do not rewrite previous artifacts or remove the generic mixed/discrete codec.

Evidence and diagnostics
- Prefer latest Analysis bo_handoff / bo_observation / experiment_evaluation over generic priors.
- Deduplicate observation IDs; retain invalid/failed evidence separately.
- Compiled-objective observations must match hash, finite score, parameters,
  feasible/fidelity/provenance and ok_for_bo eligibility.
- LIVE uses measured evidence; explicit TEST fixtures remain labelled test evidence.
- Diagnostics describe observation counts, duplicates/domain coverage and available numerical results.
- They do not calculate target attainment or trigger termination.
- Posterior standard deviation is model uncertainty, not an invented measurement uncertainty.
- retrieve_knowledge uses provided context and local-index search only, without web fallback.
- Missing local evidence remains explicitly unavailable.

Compiled objective contract
- The operator starts with research intent, not a fixed objective template.
- The LLM may compose or revise one objective_spec.v1 JSON document, but that
  output is untrusted until deterministic validation succeeds.
- The operator may instead author the same contract through Visual Builder or
  Advanced JSON. These are authoring surfaces, not alternate runtime formats.
- Required lifecycle: draft -> validate -> preview -> operator approve ->
  activate for run_id.
- Activation binds objective_id, version, and canonical objective_hash
  immutably to the run.
- Analysis is the only runtime stage that evaluates the bound expression from
  registered metrics. BO consumes the resulting objective_evaluation.v1.
- BO must not call the LLM to recalculate an existing score.

Manual objective authoring
- Route: /bo -> Bounded Objective Compiler.
- Modes: AI Compose, Visual Builder, Advanced JSON.
- Visual Builder reads GET /api/objectives/authoring-contract. Do not hardcode a
  separate frontend operator list, unit list, AST depth, or AST node limit.
- The authoring contract is derived from the deterministic compiler. Disabled
  operators such as reference remain visible to contract inspection but cannot
  be selected or accepted.
- The visual tree supports registered metric and literal leaves, unary and
  variadic expressions, named binary slots, weighted terms, aggregates,
  conditions, comparisons, Boolean constraints, and piecewise penalty points.
- Compatible subtrees may be reordered, duplicated, deleted, or reparented.
  These operations only mutate the unsaved browser draft.
- Visual Builder and Advanced JSON share one canonical last-valid spec.
- Invalid JSON must remain visible with path-specific errors. It must not
  replace the last valid visual tree or silently revert to a different draft.
- Restore Last Valid discards only the invalid JSON buffer and redraws the
  canonical visual tree.
- Unsaved manual work may be retained in browser storage across refresh. A
  successful server save clears that recovery state.
- Selecting Objective Version changes the read-only lifecycle inspection only.
  It must never overwrite the manual draft automatically.
- Load Selected as Revision is the explicit operation that copies a stored
  version into the manual builder and records its parent identity.
- POST /api/objectives/manual accepts spec, operator, and optional revision_of.
  The server assigns lifecycle=draft, created_by=operator:<name>, timestamp,
  Metric Registry version, and immutable version. Client-supplied values for
  those fields are not authoritative.
- Creating an existing objective_id without revision_of is a conflict. A
  revision must use the same objective_id and the next immutable version.
- A saved manual draft is not executable. Validate, observation Preview,
  operator Approve, and Activate for one run_id remain mandatory.
- Manual authoring never executes Python, JavaScript, shell, filesystem,
  network, Cypher, or arbitrary code supplied in the objective document.


State and artifacts
- Preserve bo_result, recommendation, next_design_request, observation_integrity,
  prior_summary, failure_model, visualization and lhs_visualization compatibility.
- New decision records contain the validated action sequence and terminal outcome.
- An accepted handoff references the optimizer candidate ID and exact parameters.
- A returned/failed decision exposes no ready Design request.
- Latest-view BO files: bo_reasoning_report.json, candidate_pool.json, bo_next_candidate.json.
- Existing archive_agent_run stores full outcomes per run/loop/attempt.
- Keep failed decision and successful numerical evidence if post-result review fails.
- Archive details: docs/runtime/loop_artifact_archiving.md.

Visualization
- LHS: lhs_design_visualization.v1; continuous/mixed domain, actual measured,
  next and planned points, initial-design progress.
- Acquisition: bo_visualization.v1; backend posterior, uncertainty bands,
  accepted observations, selected candidate and actual acquisition values.
- Do not recompute scores or GP confidence bands in the browser.
- Continuous bounds must not be presented as two discrete choices or integer cell counts.
- Signed UCB acquisition values remain signed; EI threshold annotations apply only to EI.
- Input-space coordinates belong in the LHS/domain card and backend audit data.
- The posterior is the scalar-score view on the backend normalized search path.
- Workspace, Live GUI and saved Matplotlib figures share the projection contract.
- Step selection only inspects existing records; completed-step events replace figures.
- Historical discrete plots retain their original domain semantics.

APIs and module
- GET/POST /api/bo/config: read/save settings.
- POST /api/bo/benchmark: existing numeric comparison, no LLM decision claim.
- POST /api/bo/run: registered BO Agent decision and numerical recommendation.
- /api/objectives/* remains the separate objective authoring/lifecycle boundary.
- Module tools lists experiment.benchmark; local decision tools are not global bridge tools.
- Legacy internal_graph IDs remain display/checkpoint identities, not independent schedulers.
- No new device endpoint, global transition or recovery loop is introduced.

Verification
- Domain/precision: numeric-table migration, fixed/custom bounds, invalid inputs,
  initial and next contracts, exact Design-to-geometry values, legacy compatibility.
- Decisions: permitted strategy forwarded to numeric tool; accepted versus held
  result; bad tools/args/refs/candidates rejected; successful optimization not repeated.
- Initialization: model cannot skip LHS or alter the established sequence.
- Integration: existing software-only loop and BO Workspace API fixtures.
- Visualization: production JavaScript, static browser fixture and Matplotlib artifacts.
- Real API/local model validation must use existing registered routes and be
  recorded separately from deterministic TEST; never claim physical validation.
- Current commands/results belong in the BO reference and implementation record.
