# Manipulation Pi0.5 / SARM Runtime Guideline

Status: implemented runtime guideline
Last reviewed: 2026-07-14
Scope: Manipulation Agent supervision for bounded LeRobot/Pi0.5 skills between 3DP, UTM, and disposal stages.

## 1. Role Boundary

Manipulation Agent is the robot-stage supervisor. It does not become a generic
planner and it does not construct shell commands directly.

Execution boundary:

```text
Manipulation Agent -> MCP tool lerobot.rollout.start -> LeRobotBridge -> LeRobot/Pi0.5 runtime
```

Fallback compatibility path:

```text
Manipulation Agent -> MCP tool robot.pick_place
```

Pi0.5 is treated as a bounded low-level VLA executor. Manipulation Agent owns
preflight, task selection, SARM-lite progress/risk scoring, recovery hints,
post-place Vision dependency, and downstream handoff packaging.

## 2. Bounded Manipulation Tasks

The runtime currently supports two short skills.

### `transfer_to_utm`

Purpose:

```text
Move the printed specimen from the 3D-printer output area to the UTM fixture datum.
```

Default route:

- source: `3dp_output_area`
- target: `utm_fixture`
- terminal pose: `standby_clear_of_utm`
- verification signal: `specimen_on_utm_platen`
- verified next agent: `lab_equipment_agent`

Active-cam / UTM completion route:

```text
Vision active-cam one-shot confirms ejected specimen and returns the camera route
-> Manipulation checks home/interlock through LeRobotBridge runtime contract
-> Manipulation starts policy rollout/inference
-> Vision captures UTM placement with purpose=utm_placement_verification
-> Manipulation consumes vision_manipulation_completion.v1
-> Manipulation stops the existing rollout without starting a second rollout
-> Manipulation promotes the stop response home_pose as the final post-rollout
   home/interlock check
-> robot_task_result.handoff_status=ready_for_equipment
```

Stage taxonomy:

```text
preflight -> approach_source -> pre_grasp_align -> grasp -> lift_clear ->
transfer_to_fixture -> place_on_datum -> release -> retreat -> post_place_verify
```

### `clear_utm_to_disposal`

Purpose:

```text
After UTM testing, move the tested specimen from the UTM fixture to the discard bin.
```

Default route:

- source: `utm_fixture`
- target: `discard_bin`
- terminal pose: `standby_clear_of_utm`
- verification signal: `utm_home_restored`
- verified next agent: `knowledge_agent`

Stage taxonomy:

```text
preflight -> wait_for_utm_safe -> approach_fixture ->
pre_grasp_align_tested_specimen -> grasp_tested_specimen -> lift_clear_fixture ->
transfer_to_discard_bin -> release_into_bin -> retreat ->
verify_fixture_clear_and_discarded
```

## 3. Required Inputs

From Specimen Making Agent:

- `state.run_metadata.specimen_result`
- `specimen_id`
- `candidate_id`
- `handoff_status=ready` or equivalent ready/complete status
- artifact paths when available

From Vision Agent:

- `state.latest_observations`
- `vision_signal` / `agent_signals`
- `transfer_readiness`
- anomaly state
- signal freshness (`expires_at` when available)

From operator or saved profile:

- `profile_id`
- `policy_type`
- `policy_path`, `policy_checkpoint_path`, or `policy_repo_id`
- `policy_backend`
- source/target/task override if needed
- live confirmation for physical rollout

Saved profile path:

```text
memory/manipulation_agent_bridge.json
```

## 4. Preflight Rules

Preflight produces a structured report section:

```json
{
  "status": "pass|warn|fail",
  "blocking_reasons": [],
  "warnings": [],
  "robot_ready": true,
  "camera_ready": true,
  "policy_ready": true,
  "operator_confirmed": true,
  "rtc_enabled": true,
  "action_clamp_enabled": true
}
```

Blocking conditions:

- stale or invalid Vision signal
- missing ready specimen result for `transfer_to_utm`
- missing robot profile for policy rollout
- missing live policy reference in live mode
- missing live execution confirmation in live mode
- Vision anomaly signal

Warning conditions:

- Pi0.5 selected without RTC inference
- Pi0.5 camera disabled
- action clamp disabled

## 5. Pi0.5 / LeRobot Payload

The Manipulation Agent calls `lerobot.rollout.start` with the same payload shape
used by the LeRobot GUI. Important fields:

```json
{
  "task_id": "transfer_to_utm",
  "skill_id": "transfer_to_utm",
  "policy_backend": "lerobot_cli",
  "policy_type": "pi05",
  "rollout_inference_type": "rtc",
  "rollout_rtc_execution_horizon": 10,
  "rollout_rtc_max_guidance_weight": 1.0,
  "max_duration_s": 30,
  "rollout_action_clamp": true,
  "rollout_max_relative_target": 5,
  "continuous_rollout": true,
  "camera_enabled": true
}
```

Rules:

- Live mode requires an actual policy ref and `confirm_live_execute=true`.
- Test mode may use `fake://pi05_policy` and `fake_omx_ai`.
- Manipulation Agent must not bypass LeRobotBridge or generate shell commands.
- The GUI can save defaults, but explicit experiment spec values override them.
- During the completion pass, Manipulation Agent must not call
  `lerobot.rollout.start` again when Vision provides
  `vision_manipulation_completion.v1` and an existing rollout session id. It
  calls `lerobot.rollout.stop` once and uses that stop response's runtime
  contract, including `home_pose`, for the final report state.
- For Pi0.5 live rollout, LeRobotBridge injects
  `--robot.disable_torque_on_disconnect=false` at command construction time.
  Manipulation Agent must not set this manually or store a separate arbitrary
  value. If a follower motor is missing after a rollout, the recovery path is
  motor-status inspection/reboot, not removing that motor from the expected
  ROBOTIS OMX follower ID set.
- Camera configuration is owned by LeRobotBridge profile memory. For the current
  physical setup, saved cameras should be `top=D455F` and `wrist=D405` in
  `backend=intelrealsense` mode. The bridge converts this into LeRobot
  `--robot.cameras` entries with RGB + depth/displacement at 640x480 and 15 FPS,
  yielding two RGB observation streams plus two depth/displacement streams.
  A valid RGB-D dataset must expose `observation.images.top`,
  `observation.images.wrist`, `observation.images.top_depth`, and
  `observation.images.wrist_depth` in `meta/info.json`; `use_depth=true` in the
  command alone is not sufficient evidence.
- When the operator saves `top` or `wrist` without a manual RealSense
  serial/name, LeRobotBridge must resolve the camera by SDK enumeration first:
  `top` prefers D455/D455F serials and `wrist` prefers D405 serials. This keeps
  D405 and D455F on the same RSUSB-backed `intelrealsense` runtime path.
- D405 is not a generic RGB RealSense path. The generated LeRobot camera config
  must use `color_format=bgr8` and `warmup_s>=20` for `wrist=352122273019`.
  D455F/top uses `color_format=rgb8`. Manipulation Agent must treat
  `LEROBOT_REALSENSE_ROLE_CAMERA_NOT_FOUND` and
  `LEROBOT_REALSENSE_CAMERA_UNAVAILABLE` as operator/device issues instead of
  substituting another visible RealSense camera.
- RealSense execution is SDK-only. D405 on the Spark workstation must import the
  locally built librealsense RSUSB Python binding before the default pip wheel;
  do not substitute `/dev/v4l/by-id` or OpenCV when SDK enumeration fails.
- Camera routing rule:
  follower/leader ports use persistent `/dev/serial/by-id/*` identities;
  OpenCV auxiliary cameras may use `/dev/v4l/by-id/*` or `/dev/v4l/by-path/*`;
  policy RealSense observations must use SDK serial/name through
  `type=intelrealsense`, not `/dev/video*`.
- Live camera preflight is part of the LeRobotBridge boundary. If
  `camera_enabled=true`, Manipulation Agent rollout must not start the policy
  process until the bridge verifies each saved RealSense serial in the LeRobot
  conda environment. A missing saved serial blocks with
  `LEROBOT_REALSENSE_CAMERA_UNAVAILABLE` before robot motion; the agent should
  surface that as an operator/device issue, not retry with OpenCV/V4L fallback.
- Live recording postflight is also part of the LeRobotBridge boundary. If a
  RealSense depth recording completes without the expected `*_depth` feature
  keys, the bridge returns `LEROBOT_REALSENSE_DEPTH_FEATURE_MISSING`. Treat this
  as a dataset-capture failure and do not send that dataset to Pi0.5 training as
  RGB-D.
- Spark workstation validated hardware:
  top RealSense D455F serial `341522300873`, wrist RealSense D405 serial
  `352122273019`, and Logitech BRIO by-id
  `/dev/v4l/by-id/usb-046d_Logitech_BRIO_1CD057A6-video-index0`
  currently resolving to `/dev/video6`.
- Throughput note:
  D455F + D405 at 30 FPS RGB+depth and the same pair plus BRIO 720p/15 MJPEG
  passed short stress tests, but the runtime default remains 15 FPS for
  RealSense to preserve USB and timestamp margin during recording/inference.
- Training and inference path rule:
  Manipulation Agent does not rewrite LeRobot training or rollout paths.
  Training dataset/output/checkpoint normalization is owned by
  LeRobotBridge. Rollout policy path normalization is also owned by
  LeRobotBridge: an output directory, `checkpoints/last/pretrained_model`, or a
  recognized model file is resolved to the executable `pretrained_model`
  directory before policy rollout starts.

## 6. SARM-lite Stage Supervision

SARM is a progress/risk supervisor, not an actuator controller.

Current implementation is deterministic SARM-lite:

- stage index from task taxonomy
- stage confidence from rollout/grasp proxy score
- progress score from stage progress plus rollout result
- failure precursor from progress/retry/anomaly state
- recovery hint when precursor crosses threshold

Output keys:

- `source=deterministic_stage_scorer`
- `stage_name`
- `stage_tau`
- `progress_score`
- `failure_precursor`
- `recovery_suggested`
- `rabc_weight_hint`

## 7. Post-place Vision Verification

Rollout success alone is not final physical handoff.

If LeRobot reports ok but the Vision verification signal is not present:

- `completion_status=reported_complete`
- `handoff_status=needs_post_place_vision` for `transfer_to_utm`
- `handoff_status=needs_post_disposal_vision` for `clear_utm_to_disposal`
- recommended next agent is `vision_agent`

If Vision verification is present:

- `completion_status=verified_complete`
- `handoff_status=ready_for_equipment` or `completed_disposal`
- recommended next agent is the verified downstream agent

This preserves the current graph while exposing the correct gate for the planned
post-Manipulation Vision checkpoint.

## 8. Output Contract

Manipulation Agent returns legacy keys plus structured reports:

```json
{
  "manipulation": {},
  "sarm": {},
  "manipulation_report": {"schema": "manipulation_report.v1"},
  "robot_task_result": {"schema": "robot_task_result.v1"},
  "handoff_packet": {"schema": "robot_task_result.v1"},
  "decisions": [],
  "metrics": {},
  "evidence_refs": [],
  "protocol_note": "..."
}
```

`manipulation_report.v1` sections:

- `task`
- `policy_plan`
- `preflight`
- `vision_context`
- `rollout_runtime`
- `stage_machine`
- `sarm`
- `decision`
- `knowledge_payload`
- `handoff_packet`

`robot_task_result.v1` is the compact downstream packet consumed by Vision,
Equipment, Knowledge, BO, and Guardian.

## 9. GUI Requirements

LeRobot GUI (`/lerobot`) is the Manipulation Agent management surface.

The `Manipulation Agent Bridge` panel exposes:

- task selector: `transfer_to_utm`, `clear_utm_to_disposal`
- strategy selector
- policy backend selector
- policy type selector
- policy checkpoint/repo browse
- source/target locations
- specimen/candidate IDs
- Pi0.5 RTC horizon and max guidance weight
- max duration seconds
- Vision observation JSON
- camera/display/continuous-rollout toggles
- Save Agent Defaults
- Test Agent Bridge
- Preview Agent Payload
- Run Manipulation Agent
- Stop/Status controls
- structured runtime report panel

Live GUI agent report must show the same information through the Manipulation
Agent selected-report panel without dumping raw JSON.

The Live GUI report begins with three read-only telemetry cards sourced only
from the existing rollout action log:

- `Live Robot Pose`: Isaac/Three.js visualization values only; no MotorBus open
  and no robot command.
- `Policy Tracking`: plots unmodified `latest_observation` and
  `requested_action` values. It must not substitute Isaac-converted degrees for
  these graph values. The full elapsed span remains visible under bounded
  downsampling, and each selected joint keeps a non-shrinking Y domain for the
  session.
- `Robot Motion State`: classifies measured and requested-policy evidence on two
  simultaneous axes. `home/moving` is the arm base state, while
  `grasping/ungrasping/idle` is the independent gripper state. One shared state
  track uses white glow for measured evidence and cyan glow for policy target;
  both glows remain visible when they occupy the same state.

Measured Home Gate requires a 0.5-second stable dwell and all six native values
inside these inclusive ranges:

```text
Joint1  -15 .. -6.5
Joint2  -61 .. -53
Joint3   52 .. 61
Joint4   43 .. 52
Joint5  -11 .. -3
Gripper  55 .. 65
```

Requested-policy Home is classified separately from measured feedback. It uses
the same table except `Joint2 -72 .. -65`, because the follower motor-2 limit
causes measured Home to settle in `-61 .. -53` while the policy target remains
near `-69`. Never apply the policy Joint2 range to measured interlocks, and
never substitute measured feedback for `target_source` policy annotation.

These cards are observation-only. Their state annotation does not replace the
Manipulation Agent interlock, Vision completion gate, rollout stop, or final
handoff decision.

Motion-state stability contract:

- arm enters moving at >= 4.0 native units/s
- arm motion hysteresis exits after <= 2.0 native units/s for >= 0.3 s, but a
  stable pose outside the Home ranges remains classified as moving
- gripper enters grasping/ungrasping at <= -2.0 / >= 2.0 native units/s
- gripper returns to idle only after absolute speed <= 0.5 native units/s for
  >= 0.2 s
- Home entry requires in-range arm values and low arm speed for >= 0.5 s
- measured and requested-policy channels maintain independent state latches
- grasp succeeds when the absolute measured-versus-policy Gripper gap is at
  least 2.0 native units; arm movement is retained as diagnostic evidence but
  does not override that result
- the read-only pose viewer attaches the specimen to the measured gripper on a
  successful grasp, releases it on ungrasping, and clamps a released specimen
  above the target cylinder surface so the cube cannot intersect the fixture

## 10. Test and Live Behavior

Test mode:

- calls the same ManipulationAgent path
- uses fake profile/policy when not supplied
- validates report and packet generation
- does not physically move a robot unless live execution is explicitly selected
outside the test path

Live mode:

- requires saved robot/camera identities
- requires live confirmation and profile gates
- executes only through LeRobotBridge
- surfaces action status, log tail, SARM state, and handoff decision in GUI
