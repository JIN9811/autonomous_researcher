# Codex Instructions: ATR Live GUI + Agentic Binder + LangGraph Runtime Integration

Project goal
Implement a production-grade ATR Runtime IDE for an Autonomous Researcher / Self-Driving Lab system. The interface must combine:
1. A compact Agentic Binder on the left.
2. An academic report / backend trace / graph-aware runtime panel in the center.
3. A persistent Runtime Chat on the right.
4. A bottom runtime timeline and device status strip.
5. A configurable LangGraph editor/compiler integration where visual graph edits change the actual execution graph.

The design reference images are included in:
- assets/reference/main_live_gui_reference.png
- assets/reference/graph_editor_reference.png

Use these images as visual direction, not as exact pixel-copy targets.

Primary design principle
The GUI must not be a decorative dashboard. It must be an operational runtime IDE. Every visible graph, agent tab, report section, backend trace, and chat action must map to real backend state or a defined API endpoint.

Required screen concept
Use a three-column Live GUI layout with an approximate 1:4.5:4.5 ratio.

Recommended responsive grid:
- Left: Agentic Binder, fixed compact width around 92-120 px on desktop.
- Center: Report / Backend / Graph / Artifact panel, flexible 1fr.
- Right: Persistent Runtime Chat, flexible 1fr.
- Bottom: Runtime timeline and device status spanning center/right or full width depending on available space.

Example CSS grid:
```
.live-runtime-shell {
  display: grid;
  grid-template-columns: 104px minmax(520px, 1fr) minmax(480px, 1fr);
  grid-template-rows: 72px minmax(0, 1fr) 150px;
  grid-template-areas:
    "header header header"
    "binder main chat"
    "timeline timeline timeline";
  min-height: 100vh;
}
```

Top header requirements

- Product identity: LIVE ORCHESTRATOR / Autonomous Researcher / ATR Runtime IDE.
- Run ID.
- Stage.
- Active Agent.
- Mode: TEST / DRY-RUN / LIVE.
- Status: READY / RUNNING / WAITING_USER / ERROR / SAFE_STOP / COMPLETE.
- Runtime clock.
- System health.
- GPU / VRAM / RAM / token usage compact metrics.
- Safe Stop button, always visible and visually distinct.

Status color rules:

- RUNNING: neon violet/cyan glow.
- WAITING_USER: amber pulse.
- ERROR: red border and warning icon.
- SAFE_STOP: orange/red.

Required items:

- Design Agent
- Specimen Agent

- waiting: amber pulse dot.

Click behavior:

- Double click: open backend trace for that agent.

Center panel: Academic report + backend trace dual layer
The center panel must support at least these modes:
1. Report Mode
2. Backend Trace Mode
3. Graph Mini View / Selected Node View
4. Artifact View
5. Timeline Detail View

Default mode: Report Mode.

Report Mode requirements
Each agent output must be rendered as an academic, structured report page rather than raw chat logs.
The style should be scholarly, clean, readable, and futuristic.
Use a paper-like/glass panel for report content. Avoid dumping raw LLM logs into the report.

Each Agent Report must include these sections when applicable:
- Overview / Summary
- Received Inputs
- Key Decisions
- Process Steps
- Tool Calls Summary
- Artifacts
- Validation / Quality Check
- Warnings
- Handoff
- Next Action

Example report sections:
```
Specimen Agent Report

2. Processing Steps
3. Slicing / Print Preparation
4. Quality Check
```

Each report page must have action buttons:
- BACKEND: opens backend trace drawer or center backend mode.

- Pin Finding.

- Re-run From Here if safe.

BACKEND behavior

It must show:

- Node ID.
- Handler reference.
- Raw prompt.

- Tool calls.

- Output JSON.
- Logs.

Recommended UI:
Use a right-side drawer inside the center panel or a split mode. Do not unmount the persistent Runtime Chat on the right.

Right Runtime Chat
The right column must remain a persistent Runtime Chat panel.
It must not disappear when the user switches report pages, graph editor views, backend trace, artifacts, or timelines.
The chat must be context-aware.

Runtime Chat required controls:
- Target selector: Orchestrator / Current Agent / Selected Agent / Specific Agent.
- Mode selector: Ask / Command / Approval / Edit Report.
- Conversation stream.
- Input box.
- Quick action bar.

Runtime Chat quick actions:
- Approve Next Step.
- Revise.
- Reject.
- Pause Run.
- Safe Stop.
- Dry Run.
- Explain Current Node.
- Rewrite Report Section.
- Open Backend.
- Run Node Test.

Context-aware chat behavior:
- If the user selects Analysis Agent, chat target defaults to AnalysisAgent.
- If the user opens a backend trace, chat messages can reference the current trace_id.
- If the user selects a report section, chat can rewrite, expand, or question that section.
- If a human approval is pending, the chat must surface approval/revise/reject actions.
- Follow-up messages must preserve selected agent, selected report, selected node, selected trace, and current run state.

Agent-to-user and user-to-agent follow-up
The system must support intermediate communication with agents during runtime.
Agents can request clarification, ask for approval, or ask for missing parameters.
The user can respond through the right Runtime Chat without losing the current report view.

Required follow-up event types:
- agent_question
- user_reply
- approval_requested
- approval_granted
- approval_rejected
- report_rewrite_requested
- runtime_command_requested
- node_rerun_requested
- graph_change_requested

Follow-up rules:
- Do not block the whole UI when one agent asks a question.
- Show a waiting badge on the related binder tab.
- Show an approval/question card in Runtime Chat.
- Record the exchange in backend trace and report summary.
- If the response changes graph state, trigger validation and recompile if necessary.

LangGraph integration objective
The visual graph must be operational, not decorative.
Changing visual graph structure must modify the actual execution graph through config and compiler layers.

Required architecture:
```
Frontend Graph Editor
    -> graph_config.yaml/json
    -> Backend Graph Compiler
    -> LangGraph Runtime
    -> Execution Event Stream
    -> Live GUI State Store
```

Do not make frontend directly execute Python or modify arbitrary Python files.
Frontend edits config only.
Backend compiler validates config and maps nodes to whitelisted Python handlers in the registry.

Graph features:
- Drag and drop node creation.
- Edge creation/deletion.
- Node order change.
- Conditional edge editing.
- Agent module expansion.
- Internal module graph editing.
- Assign handler from registry.
- Assign prompt template.
- Assign model route.
- Assign tool access.
- Assign input/output schema.
- Validate.
- Dry-run compile.
- Save graph version.
- Run selected graph version.
- Rollback.

Top-level graph examples:
- ATR_CLOSED_LOOP
- PRINTER_PIPELINE
- LEROBOT_PICK_PLACE
- UTM_TEST_FLOW
- CAE_OPTIMIZATION
- ANALYSIS_ONLY

Module internal graph example
When the user clicks Design Agent, the center/graph editor can show internal nodes:
- load_objective
- generate_candidates
- validate_geometry
- export_stl
- handoff_to_specimen

These internal nodes must be reorderable and configurable where safe.

Graph config example:
```yaml
graph_id: atr_closed_loop
version: 1.4.0
entry_node: orchestrator
nodes:
  - id: orchestrator
    label: Orchestrator
    module: orchestrator
    handler: agents.orchestrator.run
    input_schema: schemas.OrchestratorInput
    output_schema: schemas.OrchestratorOutput
    model_route: planner_large
  - id: design
    label: Design Agent
    module: design
    handler: modules.design.nodes.run_design
    input_schema: schemas.DesignInput
    output_schema: schemas.DesignOutput
    model_route: planner_large
edges:
  - from: orchestrator
    to: design
    type: normal
  - from: design
    to: specimen
    type: normal
  - from: guardian
    to: design
    type: conditional
    condition: retry_or_replan
```

Graph compiler requirements:
- Validate node IDs are unique.
- Validate all edge endpoints exist.
- Validate entry node exists.
- Validate no illegal cycles unless explicitly allowed.
- Validate handlers exist in registry.
- Validate input/output schema compatibility.
- Validate tool permissions.
- Validate safety constraints for live mode.
- Generate a deterministic compiled graph artifact.
- Emit compile diagnostics.

Graph versioning requirements:
- Every saved graph has graph_id, version, created_at, created_by, hash, notes.
- Every run records graph_id, version, hash.
- Runtime events include graph_version/hash.
- Allow rollback to previous graph version.

Acceptance criteria
The implementation is acceptable only if:
1. The right Runtime Chat remains mounted and preserves conversation while navigating reports/backend/graph.
2. The Agentic Binder shows running glow and unread badges.
3. Clicking an agent opens its academic report in the center.
4. BACKEND exposes raw trace without polluting the report view.
5. Graph edits save to config and call backend validation/compile endpoints.
6. Runtime events update binder, report, timeline, and chat context.
7. Human approval/follow-up requests appear in chat and binder states.
8. Live mode has clear Safe Stop access.
9. The design remains close to the provided futuristic academic reference images.

Do not implement unsafe behavior
- Do not allow arbitrary Python file editing from the browser.
- Do not run unvalidated graph configs in live mode.
- Do not hide device errors.
- Do not remove Safe Stop.
- Do not let frontend bypass backend compiler/validator.
