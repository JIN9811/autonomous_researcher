2. Correct Phase 1 Responsibility Split
============================================================

DesignAgent:
- Produces `experiment_spec`.
- Does not control the printer.
- Does not generate G-code.
- Does not decide to bypass hardware gates.

SpecimenMakingAgent:
- Remains the owner of specimen artifact preparation.
- Calls geometry and manufacturability tools first.
- Calls `printer.prepare` only after a valid handoff package exists.
- Should not directly implement PrusaLink upload/start/ejection logic.
- Should pass enough context into `printer.prepare`:
  - `specimen_id`
  - `stl_path`
  - `handoff_package_path`
  - `printer_profile`
  - `material`
  - `slicer_profile_hint`
  - optional `experiment_spec`
  - optional `print` and `ejection` request blocks

Printer tool layer (`mcp_tools/printer_tools.py`):
- Owns registration of `printer.prepare`.
- Selects simulator, virtual PrusaLink dry-run, or live workflow from config/runtime mode.
- Normalizes payloads and returns structured tool results.
- Must keep response keys stable for SpecimenMakingAgent.

Printer simulator (`device_bridges/simulator/printer_sim.py`):
- Owns deterministic test-mode print pipeline simulation.
- Must not require PrusaSlicer or a real printer.
- Should create deterministic dummy G-code/BG-code artifact metadata when an STL path exists.

Prusa bridge (`device_bridges/prusa_bridge.py`):
- Owns live PrusaLink client, slicer wrapper, safety validator, ejection builder, and job manager.
- Live write actions must be blocked unless explicitly enabled by config gates.
- Live read-only status may be allowed when explicitly configured.

Device health:
- Should continue exposing `device.health`.
- In default test mode, printer health should report simulator status.
- In test virtual-bridge dry-run mode, printer health should report deterministic virtual PrusaLink responses without touching a real printer.
- In live mode with read-only status allowed, printer health may call PrusaLink status.
- Printer unreachable must produce a structured health failure, not crash the whole runtime.

============================================================
3. Phase 1 Objective
============================================================

Primary Phase 1 objective:
- Build a safe, typed foundation for the Prusa MK4S printer workflow while preserving existing test-mode behavior.

Phase 1 must support:
1. `printer.prepare` in default test mode using simulator-backed behavior.
2. `printer.prepare` in optional test virtual-bridge dry-run mode that simulates PrusaBridge/PrusaLink communication and verifies payloads reach the physical-action boundary.
3. Live PrusaLink read-only health/status when explicitly configured.
4. Live upload, print start, monitoring, cooldown, and paddle ejection when explicit live gates are armed.
5. Hard config gates that prevent unintended physical actions in test and dry-run modes.
6. Existing full orchestration in test mode without mandatory real hardware.

Phase 1 must not:
- Start a real print by default.
- Upload a real file by default.
- Execute real ejection by default.
- Execute any physical action in `test` or virtual dry-run modes.
- Hardcode printer IP, username, password, API key, or LAN details.
- Let an LLM generate arbitrary G-code.
- Use `shell=True` for slicer or network commands.
- Remove existing mock/test behavior.
- Disable existing tests to pass.

```yaml
    simulator:

      create_dummy_gcode: true

      default_location_after_ejection: basket

      simulate_status: true
      simulate_storage: true
```

Important:
- `mode: test` must remain the default.
- `virtual_prusalink_dry_run: true` may be the default if the simulator transport is fully local and deterministic.
- On this validated local MK4S profile, `allow_upload` and `allow_start_print` are true so normal Live GUI `실험 수행` can physically print.
- Operator bed-sweep ejection is controlled by the 3DP GUI print-default profile field `allow_ejection`.
- Toolhead-paddle ejection still requires full paddle calibration; bed-sweep append ejection uses the configured MK4S bed/head coordinates and must pass `GCodeSafetyValidator` before upload.
- Secrets are resolved from environment variables or `memory/prusa_connection.json` at runtime; never hardcode them in source/config templates.

Runtime interpretation:
- `mode: live`:
  - run the normal end-to-end workflow without test-only substitution
  - route printer operations through real `PrusaBridge`
  - allow physical actions only when the corresponding live gate is true
  - actual ejection is allowed only when all ejection gates, calibration, cooldown, stop/safe-stop, and vision checks pass
- `mode: test` and `virtual_prusalink_dry_run: false`:
  - use simple `PrinterSimulator`
  - no PrusaLink-shaped request simulation
  - no PrusaSlicer requirement
- `mode: test` and `virtual_prusalink_dry_run: true`:
  - route through the same `PrinterAgenticWorkflow` and PrusaBridge interfaces used by live mode
  - use a virtual/local PrusaLink transport instead of real network I/O
  - simulate status/version/storage/job/transfer responses
  - build and validate upload/start/ejection request payloads up to the physical-action boundary
  - return upload/start/ejection as `virtual_ack`, `dry_run_blocked`, or `not_enabled`
  - never perform live network write actions regardless of live allow flags
- `mode: test` with printer-live promotion enabled:
  - the overall run remains test mode
  - when `SpecimenMakingAgent` reaches `printer.prepare`, emit a GUI/event message that printer connectivity is being checked
  - perform a read-only connectivity probe through PrusaLink if host/auth config is present and status probing is allowed
  - if the printer is reachable and operator/config gates allow it, promote only the printer subsystem to live mode for this specimen preparation
  - all non-printer stages remain test/simulated
  - if the printer is not reachable, not configured, or not approved, continue through the virtual PrusaLink dry-run path
  - never silently promote the whole workflow to live mode from a test run

6. PrusaLink Client Requirements
============================================================

`PrusaLinkClient` must provide typed methods:
- `get_version()`
- `get_status()`
- `get_storage()`
- `get_job()`
- `get_transfer()`
- `get_file_metadata(storage, remote_path)`
- `upload_file(local_path, storage, remote_path, overwrite=False, print_after_upload=False)`
- `start_file(storage, remote_path)`

Behavior:
- Build URLs safely from `scheme`, `host`, `port`, and path.
- Resolve host and secrets from env vars at call time.
- Support auth modes:
  - none
  - api_key header
  - basic
  - digest if the chosen HTTP client supports it cleanly
- Use connect/request/upload timeouts from config.
- Return structured errors for:
  - missing host
  - connection failure
  - timeout
  - unauthorized
  - non-2xx response
  - storage unavailable / read-only / not found
  - invalid JSON
- Never log passwords, API keys, or full auth headers.
- Digest-auth uploads must use a replayable bytes payload, not a one-shot generator stream, because the HTTP client may perform an initial challenge and replay the request body.
- `GET /api/v1/storage` should be checked before live upload. If the selected `storage` entry reports `available: false` or `read_only: true`, block with `PRINTER_STORAGE_UNAVAILABLE` or `PRINTER_STORAGE_READ_ONLY` before uploading.
- `PUT /api/v1/files/{storage}/{path}` returning HTTP 507 must be normalized to `PRINTER_STORAGE_UNAVAILABLE`; on MK4S this was observed when USB storage was not writable/available.
- After a successful live upload, the workflow must poll `GET /api/v1/transfer` until it is idle/empty before calling `start_file`. This avoids the intermittent race where the file appears in storage but PrusaLink has not finished USB transfer/indexing.
- After transfer idle, every physical start path must read `GET /api/v1/files/{storage}/{requested_remote_path}` and start the returned storage filename from metadata (`payload.name`, e.g. `AUTOEJ~1.GCO`). Do not directly start the requested/display filename when PrusaLink has converted it to an 8.3 USB filename.
- If metadata cannot be read for a physical start, block with a structured failure instead of falling back to the requested/display filename. Virtual transport may keep using the requested path.
- If `start_file` returns a retryable non-2xx response after upload, retry the start call after rechecking transfer-idle state. The returned `print_result` must include `transfer_wait` and `start.retry_history` diagnostics.

Phase 1 live gate rules:
- `get_status`, `get_storage`, `get_job`, `get_transfer` may run only when:
  - `devices.printer.mode == live`
  - `devices.printer.live.allow_status == true`
- `upload_file` must refuse before any network call unless:
  - `allow_upload == true`
- `start_file` must refuse before any network call unless:
  - `allow_start_print == true`
- Ejection-related live calls must refuse unless:
  - `allow_ejection == true`
  - `devices.printer.ejection.enabled == true`

8. G-code Safety Validator Requirements
============================================================

`GCodeSafetyValidator` must validate ejection G-code strictly.

Allowed ejection command set should be small and explicit:
- `G0`
- `G1`
- `G4`
- `G28`
- `G90`
- `G91`
- `M73`
- `M400`
- `M104`
- `M140`
- `M190`
- `M107`
- `M84`

Rules:
- Reject unknown G/M commands.
- Reject extrusion moves if `E` is present.
- Reject coordinates outside configured safe envelope.
- Reject feedrates above configured max if a max exists.
- Reject heating commands:
  - `M104 S200` must fail.
  - `M140 S60` must fail.
- `M190 R<temp>` is allowed only when `<temp> <= max_bed_temp_c`; this is used by the bed-sweep append routine to wait for the bed to cool before ejection.
- Heater commands are only allowed for turning heaters off:
  - `M104 S0`
  - `M140 S0`
- Reject missing paddle calibration values before generating toolhead-paddle live ejection G-code.

Return structured validation:

```python
{
  "ok": False,
  "failure_code": "GCODE_UNSAFE_COORDINATE",
  "violations": [...],
}
```

Print G-code validation in Phase 1:
- Keep lightweight.
- Confirm file exists.
- Optionally scan for project-forbidden commands.
- Do not try to fully parse every PrusaSlicer command in Phase 1.

9. Toolhead-Mounted Paddle Ejection Builder
============================================================

`PaddleEjectionRoutineBuilder` must:
- Require `method == toolhead_paddle`.
- Require all calibration values.
- Generate G-code only from a deterministic template.
- Never use the nozzle tip as the pusher.
- Never include heat-up commands.
- Treat print job and ejection job as logically separate.
- Validate generated G-code with `GCodeSafetyValidator` before returning it.

Conceptual template:

```gcode
; AUTO-GENERATED PADDLE EJECTION ROUTINE
; calibration_id={calibration_id}
M400
M104 S0
M140 S0
G90
G1 Z{safe_z_mm} F1200
G1 X{sweep_start_x_mm} Y{sweep_start_y_mm} F3000
G1 Z{sweep_z_mm} F600
G1 X{sweep_end_x_mm} Y{sweep_end_y_mm} F{sweep_feedrate_mm_min}
G1 Z{safe_z_mm} F1200
G1 X{park_x_mm} Y{park_y_mm} F3000
M400
```

All numeric values must come from config/calibration.
Do not hardcode live ejection geometry.

9A. Bed-Sweep Append Ejection Builder
============================================================

Current MK4S auto-ejection option:
- `devices.printer.ejection.method: bed_sweep`
- `devices.printer.ejection.mode: append_end_gcode`
- Operator toggle: `memory/prusa_print_profile.json` -> `allow_ejection`

Runtime behavior:
1. PrusaSlicer generates normal print G-code.
2. The bridge validates the sliced G-code exists.
3. If `ejection.enabled=true` is supplied by the GUI/profile-driven run payload, the bridge builds a deterministic bed-sweep ejection tail.
4. The bridge validates the ejection tail with `GCodeSafetyValidator`.
5. The bridge writes `<specimen>.autoeject.gcode`.
6. PrusaLink upload/start uses the `.autoeject.gcode` file, not the original sliced file.

Deterministic template:

```gcode
; AUTO-GENERATED BED-SWEEP EJECTION ROUTINE
; adapted_for=Prusa MK4S Buddy firmware
; calibration_id={calibration_id}
M400
M190 R{cooldown_bed_temp_c}
G90
G0 Y{bed_forward_y_mm} F{travel_feedrate_mm_min}
M73 P99 R0
M73 Q99 S0
G0 X{head_center_x_mm} F{travel_feedrate_mm_min}
G0 Z{head_z_mm} F{z_feedrate_mm_min}
G0 Y{bed_back_y_mm} F{eject_feedrate_mm_min}
G0 Y{bed_forward_y_mm} F{travel_feedrate_mm_min}
G0 Y{bed_back_y_mm} F{eject_feedrate_mm_min}
G28 X Y
M84 X Y E
M104 S0
M140 S0
M400
M73 P100 R0
M73 Q100 S0
```

Default MK4S bed-sweep values:
- `cooldown_bed_temp_c: 40`
- `bed_forward_y_mm: 210`
- `bed_back_y_mm: 6`
- `head_center_x_mm: 125`
- `head_z_mm: 1`
- `travel_feedrate_mm_min: 3000`
- `z_feedrate_mm_min: 1000`
- `eject_feedrate_mm_min: 25000`
- `cycles: 2`

Safety notes:
- This routine assumes a print shape that can release after bed cooldown; it is not guaranteed for every material/geometry.
- It must stay behind the operator profile toggle, which is materialized in the run payload as `ejection.enabled=true`.
- The appended G-code is the only physical ejection path for this bed-sweep mode; no separate ejection job is started.
- The final `M400` plus `M73 P100/Q100` markers are required so the MK4S UI/progress state closes cleanly after the appended ejection tail. Earlier 99% markers are only the transition into the ejection tail.
- Ready-state transition is observed through PrusaLink status/job, not forced through G-code or a SetReady API. Before every physical start path, the bridge checks PrusaLink status/job. It must never start a new job while a previous `PRINTING` job remains at 99% or 100%, because the appended autoejection tail may still be executing homing or bed-sweep moves. The bridge waits until `/api/v1/job` is cleared and the printer reports idle/FINISHED before the next upload/start.

Reference basis:
- Operator-provided MK4S auto-ejection video/G-code snippet.
- Prusa Buddy firmware command documentation for MK4-family `G0/G1`, `G28`, `M73`, `M84`, and `M190`.
- Marlin temperature command documentation for `M190 R<temp>` wait-for-heating-or-cooling semantics and `M140` non-waiting bed target behavior.
- PrusaLink source exposes a local SetReady route in some deployments, but the validated MK4S embedded PrusaLink 2.1.2 target returned 404 for `POST /api/printer/ready` and `/api/v1/printer/ready`. Local MK4S observation showed autoejection jobs can remain at `PRINTING`, `progress=99` and later `progress=100`, `time_remaining=0`, with heaters off while final G-code is still settling. These states are not safe for a new start. Wait for `/api/v1/job` to return 204 before starting the next file.

12. Safety and Guardrail Rules
============================================================

Hard-block:
- Live upload unless `allow_upload == true`.
- Live print start unless `allow_start_print == true`.
- Live ejection unless:
  - `allow_ejection == true`
  - `ejection.enabled == true`
  - calibration values are complete
  - generated ejection G-code passes validator
- Ejection if bed temperature is unknown or above `max_bed_temp_c` when cooldown is required.
- Ejection if printer state is not idle/finished.
- Ejection if `state.stop_requested` or `state.safe_stop_requested` is true and available.
- Ejection if pre-eject vision is required but no pre-eject verification is available.

Return structured errors instead of leaking internal exceptions into the tool result.

RAG-derived operational facts:
- PrusaLink is a local-network interface for printer monitoring, file upload, and print control.
- The OpenAPI spec defines read endpoints used by Phase 1:
  - `GET /api/version`
  - `GET /api/v1/status`
  - `GET /api/v1/storage`
  - `GET /api/v1/job`
  - `GET /api/v1/transfer`
- The OpenAPI spec defines the file action boundary:
  - `PUT /api/v1/files/{storage}/{path}` uploads a file.
  - Upload uses `application/octet-stream`.
  - Upload headers include `Overwrite` and `Print-After-Upload` as structured booleans `?0` or `?1`.
  - `POST /api/v1/files/{storage}/{path}` starts printing the uploaded file when no job is running.
- PrusaLink 0.7.0 release notes call out the newer v1 endpoints and the preferred PUT upload path.
- PrusaSlicer has a CLI, but the upstream CLI wiki warns that `--help` is the current source of truth.
- For CLI slicing, PrusaSlicer can load project/profile data from AMF/3MF, and command-line parameters override imported values.

Implementation-level decisions for this repository:
- DesignAgent remains the only stage that should render STL geometry previews in Live GUI.
- SpecimenMakingAgent must not show the STL viewer again.
- SpecimenMakingAgent should show:
  - PrusaSlicer input model path
  - output G-code path
  - printer profile
  - material
  - slicer profile hint
  - final `layer_height_mm` from `experiment_spec`, with `slicer_profile_hint` inference only as fallback
  - final `nozzle_diameter_mm` from `experiment_spec`, with `printer_profile` inference only as fallback
  - final `cell_size_mm`, `relative_density`, and `expected_mass_g` from the selected Design Agent candidate
  - resolved PrusaSlicer command template
  - PrusaLink transport and endpoint shape
  - `printer.prepare` step trace
  - upload/start/ejection gate result
- `PrusaSlicerRunner` supports `profile_map` so a configured command template may include `--load {profile_path}` without changing agent code.
- Default slicer command remains minimal and safe:
  - `{executable} --export-gcode --output {output_path} {stl_path}`
- If a local production profile is needed, set for example:

```yaml

  printer:
    slicer:
      enabled: true
      executable_env: PRUSA_SLICER_EXECUTABLE

        0.2mm_quality: configs/prusa_profiles/mk4s_pla_0p20_quality.ini
```

Runtime adhesion geometry policy:
- The 3DP GUI exposes skirt/brim/raft as an operator option.
- Default profile sets `skirt_enabled=false`.
- When `skirt_enabled=false`, the bridge appends `--skirts=0 --brim-width=0 --raft-layers=0` to the PrusaSlicer command so auxiliary adhesion structures are not printed around the specimen.
- TPMS cap skins are separate specimen-geometry options: default bottom-only `bottom_cap_enabled=true`, `top_cap_enabled=false`, `top_bottom_cap=true`, `skin_thickness_mm=0.8` for bed adhesion. Enable the top cap only for explicit flat upper compression-face requirements; disabling both caps is allowed when the operator explicitly wants bare TPMS output.
- Auto-ejection bed sweep must parse the sliced G-code extrusion moves before appending the tail. Use the derived object bounds to set the nozzle X position to the printed object's center (`resolved_head_x_mm`) and report `object_bounds` / `head_x_source` in `ejection_result`. Keep the full configured Y sweep for physical ejection distance unless a separately validated calibration changes it.
- Standalone 3DP GUI autoejection tests for left/center/right must use the same bed-sweep ejection builder and safety validator. They may inject synthetic object bounds and run ejection-only G-code, but they must not use a separate unvalidated motion program or include specimen-printing extrusion moves.

Live safety gates remain authoritative:
- `allow_upload=false` blocks before any upload network call.
- `allow_start_print=false` blocks before any print-start network call.
- In the current local profile these two gates are true so normal Live GUI `실험 수행` can upload/start.
- `allow_ejection=false` or incomplete ejection calibration blocks ejection.
- Test-mode virtual bridge may build and display PrusaLink-shaped upload/start/ejection requests without touching a real printer.
- Test-mode installed-printer communication may run real PrusaSlicer slicing and read-only PrusaLink status/storage/job/transfer checks, but upload/start remain blocked.
- Test-mode `physical_print` / `실제 출력` is the explicit exception: it runs real PrusaSlicer slicing and may upload/start the test-generated specimen through PrusaLink when live gates and connection memory allow it.

Current production-readiness target:
- A real PrusaSlicer executable and local profile path can be configured without modifying agent code.
- A real PrusaLink host/auth can be configured through `memory/prusa_connection.json` or environment variables without hardcoding secrets.
- Live GUI should expose the exact slicer settings, PrusaLink storage readiness, upload/start result, and step trace instead of only a final "completed" line.
- The STL viewer belongs to DesignAgent; SpecimenMakingAgent owns slicing and printer runtime visibility.
- During Live GUI handoff, `printer.prepare` may emit per-step runtime events so the chat can show `PRECHECK`, `SLICE`, `UPLOAD`, `START_PRINT`, `AUTO_EJECT`, and related gate states while the tool is running.

- Status endpoint:
  - `GET /api/v1/status`
- Storage endpoint:
  - `GET /api/v1/storage`
- Upload endpoint:
  - `PUT /api/v1/files/usb/<file>.gcode`
- Metadata endpoint:
  - `GET /api/v1/files/usb/<requested-file>.gcode`
- Start endpoint:
  - `POST /api/v1/files/usb/<metadata.name>`
  - Example: requested/display filename `autoeject-test-center.gcode` resolves to `AUTOEJ~1.GCO`, and the validated start endpoint is `POST /api/v1/files/usb/AUTOEJ~1.GCO`.
- Upload headers:
  - `Content-Type: application/octet-stream`
  - `Overwrite: ?1` or `?0`
  - `Print-After-Upload: ?0` for staged upload/start separation
- Upload/start order:
  - check `GET /api/v1/status` and `GET /api/v1/job`
  - if a previous physical job is active, wait until `/api/v1/job` clears and status returns idle/FINISHED
  - upload with staged separation
  - poll `GET /api/v1/transfer` until HTTP 204 or an idle/completed payload
  - read file metadata and resolve the actual storage filename
  - then `POST /api/v1/files/usb/<metadata.name>`
  - after every start request, poll `GET /api/v1/status` and `GET /api/v1/job` to confirm `PRINTING`
  - if `PRINTING` is not confirmed, retry the start request every 1 second while recording retry history
- Successful upload status observed:
  - HTTP 201
- Successful print-start status observed:
  - HTTP 204
- Successful final print state observed:
  - `FINISHED`

Storage failure rule learned from validation:
- `GET /api/v1/storage` may return a `storage_list` entry for USB with `available: false`.
- In that state, `PUT /api/v1/files/usb/<file>.gcode` can fail with HTTP 507 and text similar to "Failed to write to location".
- The bridge must block or normalize this as `PRINTER_STORAGE_UNAVAILABLE`, not a generic HTTP failure.
- Operator action is to insert/enable writable USB storage, then rerun upload/start.
